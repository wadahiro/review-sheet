# cdk-snapshot — review-sheet for pre-rendered per-environment artifacts

This example reviews an **AWS CDK** stack whose per-environment divergence lives
in **program logic**, not in per-environment files:

```ts
const prod = props.stage === "production";
memorySize: prod ? 1769 : 512,
timeout: Duration.seconds(prod ? 30 : 10),
```

There is no `staging.yml` / `production.yml` to lay over a base — the resolved
values for each environment exist only in what the tool renders. So the
workflow flips: **pre-render one artifact per environment** (`cdk synth`), commit
them, and let the `snapshot` recipe read each artifact as that environment's
column.

The same shape covers `terraform plan -json` per workspace, `helm template` per
values file, `cdktf synth`, `pulumi stack export` — anything that resolves
program logic into a flat declarative artifact, one per environment.

Generating the sheet needs only **bun** (the committed templates in
`snapshots/` are the input; no AWS account, no CDK toolchain):

```sh
bun run ../../src/cli.ts import --spec review-sheet/build.yml -o input.json
bun run ../../src/cli.ts generate -i input.json -o sheet.html
```

## What this example demonstrates

- **Snapshot review**: one artifact per environment, no base layer, so **every
  parameter is Pattern B** (one value column per environment).
- **Partial Pattern B**: production has a read-autoscaling resource that staging
  does not, so those rows show a production value and a **blank staging cell** —
  the divergence is the review-worthy fact, not an error.
- **Selecting a reviewable subset** of a machine-generated artifact with
  `include` / `exclude` path globs.
- **Read-only by construction**: the artifact is regenerated by the next
  `synth`, so every value is marked `source.generated` and `apply` **holds** the
  change for the AI prompt / manual edit instead of writing into the template.
- **Project-authored descriptions**: there is no product dictionary for "a
  CloudFormation template", so `review-sheet/sheet.yml` carries the category and
  a bilingual description for each of the 19 reviewed parameters.

## Layout

```
app/                    the CDK stack (illustrative — nothing reads or runs it)
  api-stack.ts          `prod ? … : …` — where the divergence actually lives
  app.ts                one stack per stage
snapshots/              committed `cdk synth` output, one template per stage
  StagingApiStack.template.json
  ProductionApiStack.template.json
review-sheet/
  build.yml             the snapshot recipe: instances -> artifacts, include/exclude
  sheet.yml             project metadata: category + bilingual description per key
```

In a real project the artifacts are refreshed by re-running the toolchain and
committing the result:

```sh
cdk synth --output snapshots      # or: terraform plan -out … / helm template …
```

`import --spec` never executes a toolchain — the artifacts are ordinary
committed files — which keeps sheet generation hermetic and offline. Commit them
(as here, so the sheet is reproducible from the repo alone) or render them in CI
immediately before `import`.

## What the sheet contains

Every parameter is keyed by its **structural path in the template**
(`Resources.ApiFunction4A2B0C1D.Properties.MemorySize`), because a synthesized
artifact repeats leaf names (`Timeout`, `RetentionInDays`) across resources —
the leaf alone is not an identity.

| Category | Parameters | Notes |
| --- | --- | --- |
| Data store | 6 | capacity, PITR, encryption, `DeletionPolicy` (Retain in prod, Delete in staging) |
| Scaling | 4 | **production only** — the whole `ScalableTarget` resource is absent from the staging template |
| Compute | 6 | memory/timeout/log level differ per stage; `ReservedConcurrentExecutions` is production-only; `Handler` is `out_of_scope` (fixed by the platform team's template) |
| Logging | 3 | log group name and retention (7 days vs 1 year) |

Values identical in both environments (`BillingMode`, `SSEEnabled`, `Runtime`)
stay Pattern B rather than collapsing into a single shared row: with independent
artifacts there is no evidence that the sameness is *intended*, and each
environment's value has its own source location. Two columns showing the same
value is the honest rendering — and it is exactly what you want to see when one
of them later drifts.

### Selecting what to review

A synthesized template carries far more scalars than anyone reviews (bootstrap
parameters, asset hashes, IAM trust policies, `Ref`/`Fn::*` intrinsics that only
resolve at deploy time). `build.yml` selects by structural path — `*` matches
within one path segment, `**` crosses segments:

```yaml
include:
  - "Resources.*.Properties.**"
  - "Resources.*.DeletionPolicy"
exclude:
  - "Resources.ApiFunctionServiceRole*.**"   # IAM wiring: reviewed elsewhere
  - "**.KeySchema**"                          # table schema, not a tunable
  - "**.Code.**"                              # asset bucket/key
  - "**.Ref"                                  # intrinsics resolve at deploy time
  - "**.Fn::**"
```

Anything not selected is dropped **before** assembly, so it never reaches the
sheet and never needs a description. Anything selected does: `import --spec` is
strict, so a parameter with no description in `sheet.yml` fails the build by
name — which is how the reviewed set stays deliberate rather than accidental.

`exclude` is noise reduction, not scope. A parameter you *did* review and
consciously excluded from your remit belongs in `sheet.yml` with `out_of_scope`
(`reason` mandatory, `owner` optional) — like `Handler` here — so it stays
visible, greyed out, with the reason attached.

## Read-only, and why

The recipe marks every extracted value `source.generated: true`, and `build.yml`
declares `capabilities: { apply: false }`. Together:

- the viewer drops the apply affordance for the whole sheet;
- `apply` **holds** any change with *"Cannot apply directly: source file is
  generated"* and routes it to the AI prompt / manual fallback instead of
  editing the template — an edit written into `snapshots/…json` would be
  silently overwritten by the next `cdk synth`;
- `verify` still checks every source map against the real artifact, and
  downgrades a *missing* artifact to a warning (it is a build product).

The change belongs in `app/api-stack.ts`. The sheet tells you **what** to change
and in **which environment**; the prompt carries that to whoever (or whatever)
edits the source.

## The trade-off vs. annotating the source

[`../cdk-annotations`](../cdk-annotations) reviews the same kind of stack from
the other side: `@rs` comments on the CDK source, where `apply` edits the
**program** in place. The two are complementary:

| | `cdk-annotations` | `cdk-snapshot` (this example) |
| --- | --- | --- |
| Subject | the source you own | the artifact that actually deploys |
| Values | source expressions (`Duration.seconds(30)`) | resolved values (`30`) |
| Per-environment | `@rs:config instance:` on per-env literals | one artifact per environment, always |
| Computed values | not mappable (no literal to point at) | fully covered — the tool already resolved them |
| `apply` | edits the source | held (the artifact is regenerated) |
| Curation | inherent (you annotate what matters) | `include`/`exclude` + strict descriptions |
| Needs | ability to edit the program | a working toolchain to render the artifact |

One caveat specific to this workflow: CDK derives logical IDs from the construct
path, so **renaming a construct changes the parameter key** — the sheet's version
history then shows the parameter as removed + added rather than changed. That is
the price of reviewing an artifact nobody hand-writes.

`input.json` and `sheet.html` are generated artifacts (git-ignored); regenerate
with the two commands at the top.
