# ansible-keycloak

A review sheet for a single **Keycloak 26.7.0** Ansible role, deployed as a
systemd service on the RHEL family and configured through `keycloak.conf`
(Quarkus). Two things make it distinctive among the examples: it reviews the
**product's configuration in the product's own vocabulary** (not the Ansible
variable names), and its dictionary is **extracted from the product itself**.

## What this example demonstrates

- **The sheet is the full inventory of the product.** `materialize` expands the
  extracted dictionary: of its 257 Keycloak options, 18 are set by the role and
  121 more become rows at Keycloak's own default (`origin: default`, filed under
  Keycloak's own category); the remaining 118 have no documented default, which
  materialize excludes rather than invent one for. This is the case materialize
  is made for — the dictionary is a genuine full extraction (Keycloak's own
  `PropertyMappers` registry, read inside the official image), and because the
  sheet is keyed by the product's config keys, the dictionary's key space and
  the sheet's are the same one, so nothing is duplicated and no category is
  invented.


- **The sheet reviews Keycloak's config keys, not the Ansible variables.** Each
  parameter's `key` is the `keycloak.conf` key (`db-url`, `hostname-strict`, …) —
  what an operator, auditor, or the Keycloak docs actually call it, and the same
  key the extracted dictionary uses. The Ansible variable that backs the value
  (`kc_db_url`) is **provenance, not a second identity**: the value `source`
  points at the `group_vars` / `defaults` line (so `apply` writes back there),
  and the variable is shown as a muted **sub-line inside the key cell** (`db-url`
  with `kc_db_url` beneath it) — tied to the key, costing no column width and
  staying visible whenever the key is (a `place: under_key` column, not a
  trailing one). Keying by the product concept keeps the sheet's history stable if
  the delivery mechanism ever changes (Ansible → Helm → …) and means **no
  `dict_key` aliases**: the key already matches the dictionary.

  This is the counterpoint to `ansible-basic` / `ansible-httpd`, which review the
  Ansible **variables** (config-as-code view, with `dict_key` aliases and
  `argument_specs`). Same tool, two legitimate review subjects.

- **The config-key ← variable map is read from the template, not hand-authored.**
  The `ansible` recipe parses `keycloak.conf.j2` (`db-url={{ kc_db_url }}`) to learn which
  Ansible variable backs each config key, then source-maps the value to that
  variable's definition. Keycloak's *unified per-source* format means one option
  is spelled differently per source; the role renders the **configuration-file
  format** (kebab-case, no prefix), which lines up with every other form:

  | Source | `db-url` example |
  | --- | --- |
  | CLI | `--db-url=<value>` |
  | Environment variable | `KC_DB_URL=<value>` |
  | **keycloak.conf (this role renders this)** | `db-url=<value>` |
  | KeyStore | `kc.db-url` |
  | Ansible variable (backs the value; shown as provenance) | `kc_db_url` |

- **Dictionary extracted from the product** (not hand-authored, not from docs).
  `review-sheet/metadata/keycloak@26.7.0.yml` is generated by
  `review-sheet/metadata/build-dict.ts` from a JSON snapshot that the
  [`keycloak-config-extractor`](https://github.com/wadahiro/agent-skills) skill
  produces by reading Keycloak's own **`PropertyMappers` registry inside
  `quay.io/keycloak/keycloak:26.7.0`** — the registry the server itself consults
  to decide whether a `kc.*` key exists.
  That is the whole point: an extraction that merely reflects over the
  `org.keycloak.config.*Options` classes (what this example did until it was
  measured against `kc.sh start --help-all`) misses every wildcard key
  (`db-username-<datasource>`, `log-level-<category>`) and any Options class the
  extractor's list forgot, and parsing `--help-all` instead misses every hidden
  option — either way you get a `coverage: full` claim over a partial ledger.
  The one thing genuinely outside the extraction is `spi-*`, which is open-ended
  by design; the generated dictionary's header says so. Every default and
  English description is the product's own — `provenance: extracted`. This is the
  container-reflection analogue of `ansible-basic`'s `pg_settings` extraction, and
  it is the sheet's only metadata source: since the sheet reviews product config
  keys, the product's own self-description is the authoritative documentation.
  (The role still ships `meta/argument_specs.yml` as good Ansible practice, but
  the sheet does not consume it — argument specs document the `kc_*` variables,
  not the product keys.)

- **Build-time vs runtime scope.** Keycloak bakes some options at `kc.sh build`.
  The extractor records `build_time`, which the dictionary surfaces as
  `scope: build-time | runtime` so reviewers see which knobs can't change at
  start.

- **Per-parameter `out_of_scope`.** `db-password` is a secret (Vault in real
  projects), so it is marked `out_of_scope` **at parameter granularity** in
  `sheet.yml` — an object with a mandatory `reason` (why it's excluded from
  *this* review) and an optional `owner`:
  `{ reason: "Ansible Vault で管理されるシークレットのため、平文でのレビュー対象外", owner: "DBA/Secrets" }`.
  Shown for completeness but never surfaced or edited as plaintext. `out_of_scope`
  is a review-remit boundary, not a statement about mechanism — the `db` key
  (also a template literal, `db=postgres`) is *not* out_of_scope: it is an
  ordinary in-scope parameter with `origin: embedded`. `assembleSheets`
  propagates the project metadata's `out_of_scope` object onto the emitted parameter.

- **Bilingual descriptions + language toggle.** Dictionary descriptions are
  `{ en, ja }` for the reviewed subset, so those rows switch with the viewer's
  language toggle; keys with no Japanese fall back to English.

## Layout

```
roles/keycloak/
  defaults/main.yml         # kc_* variables (back the reviewed values)
  vars/main.yml             # pinned version + install identity (not reviewed)
  templates/keycloak.conf.j2  # Quarkus key=value; {{ kc_* }} + embedded literal (db=postgres)
  templates/keycloak.service.j2
  meta/argument_specs.yml   # role's own variable docs (good practice; not used by the sheet)
inventories/{staging,production}/group_vars/keycloak.yml  # per-env overrides (Pattern B)
review-sheet/
  sheet.yml                 # project metadata: categories + out_of_scope, keyed by config key (no aliases)
  metadata/build-dict.ts    # normalizer: extraction JSON -> dictionary yml
  metadata/keycloak-defaults-26.7.0.json  # extractor output (product self-description)
  metadata/keycloak@26.7.0.yml            # GENERATED dictionary (257 keys, 18 bilingual)
  build.yml                 # declarative build spec (config key <- Ansible variable; "ansible" recipe)
```

## Run it

```sh
cd examples/ansible-keycloak

# 1. (Re)generate the product dictionary — only needed on a Keycloak upgrade.
#    Requires Docker; pulls the official image and reads its own config registry.
#    Via the skill:  /wadahiro-agent-skills:keycloak-config-extractor 26.7.0
#    Or directly:
#      bash <skill>/scripts/extract.sh 26.7.0 --server \
#        > review-sheet/metadata/keycloak-defaults-26.7.0.json
bun run review-sheet/metadata/build-dict.ts
#   -> wrote keycloak@26.7.0.yml (257 params, 18 translated, 8 community-described,
#      11 hidden, 7 deprecated, 4 excluded as non-configuration)

# 2. Assemble the sheet (map config keys to their variables, enrich, verify).
bun run ../../src/cli.ts import --spec review-sheet/build.yml -o input.json
#   -> metadata: 138 parameter(s) enriched (dictionary:544)
#   -> verify: 24 ok, 0 warn, 0 error, 0 unmapped, 1 out-of-scope, 121 product-default

# 3. Generate the HTML (ja default; the in-page toggle switches en/ja).
bun run ../../src/cli.ts generate -i input.json -o sheet.html --lang ja
```

`input.json` and `sheet.html` are git-ignored; the dictionary and its extraction
snapshot are committed so the sheet reproduces without Docker.
