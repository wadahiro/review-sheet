# Architecture

Loaded when working under `src/` or `tests/`. This is the per-module record of
WHY each piece is shaped the way it is — the part that cannot be recovered by
reading the code, only the part that can be re-derived from it was cut.


- `src/compose.ts` — several recipes, ONE sheet (`parts:`). A page of an incumbent parameter sheet is a host, and which of its files this tool reads as Ansible variables and which as lines of a rendered artifact is an accident of the build — with one recipe per sheet that accident chose the tab layout. Each part is a finished SheetInputs by the time it arrives, so the merge is pure. The safety is entirely in COMPONENT scoping, which the model already had: rows are unique within a component, so two parts can only collide by both claiming one, and that is reported (naming both parts — every part carries the SHEET's name, so the name cannot tell them apart and a report using it names both sides identically) rather than resolved by last-write-wins. Layers are REBUILT rather than concatenated because each part hands over a base of its own and assembleSheets requires exactly one; an overlay restates a key the base already has and is not a second claim on it. What a sheet can only have one of — a dictionary key rewrite, a document — is refused with the way out named, never silently taken from the first part
- `src/html/generate.ts` — packages app JS + CSS + data JSON into a single HTML file. Everything it embeds goes through `escapeScriptClose` first: a `</script>` anywhere in the text ends the element and the rest of the document becomes markup, which reads as a blank page. Not hypothetical — the app's own source contains that literal (it reads its embedded history back out), and any config value could too. The escaping belongs HERE, to whoever writes the `<script>` element, rather than to each producer of text: every caller getting it right separately is exactly how it went wrong
- `src/html/app.ts` — browser-side Preact app (rendering + review UI). Exports `Root`/`App` for `tests/viewer.test.ts` (DOM tests; `init()` is a no-op without the embedded elements, so importing it is safe). Review state is durable or it is not kept: what a pass over a sheet produces is
review items, `out_of_scope` in the hand-authored sheet.yml, and the commit
itself. A session-local "I have looked at this" column was tried and removed — a
per-row read-marker is a value snapshot of the sheet in a worse format than the
committed input.json already is, and "what still needs re-reviewing" is
`diff(reviewed revision, now)` (`review-sheet diff`, or Compare)
- `src/html/app.ts`'s **`ArtifactPanel`** — the deployed file, beside the sheet. A value cannot be judged alone: `StartServers 2` is right or wrong depending on the `<IfModule mpm_event_module>` around it, and a container is NOT a row (no value, no definition site, nothing to review), so the file goes next to the sheet rather than its brackets becoming parameters. A PINNED right-hand panel and not a modal, deliberately: the requirement is to review a setting WHILE seeing its context, and a full-screen overlay shows the context INSTEAD of the row — the problem it was there to solve. It is a LENS, not data: no review affordances, no source maps of its own, no place in the search index; the rows stay the only reviewable values. The one thing it does besides scroll-and-highlight is the inverse jump (click a line, land on its row) — and when that row is not rendered, which is almost always because it is a product default behind the unset-rows toggle, the jump turns the toggle on and retries on the next macrotask rather than doing nothing: a click that silently accomplishes nothing is the same failure as an affordance that opens nothing, and the reader has just pointed at the line, found by DOM id because only the rendered tree knows which category path a key ended up under. A preview line's `key` is stripped by the assembler when no row of that sheet survived under it: a recipe builds previews before assembly has finished deciding which rows exist (a dictionary's `ui: "absent"` drops one, a filter removes another), so a line can be left naming a row that is not there and clicking it does nothing — the same "an affordance that opens nothing is worse than none" rule the row side follows, seen from the other end. Measured: 13 lines across two sheets, every one a field the product's own console does not have. The row->preview index is keyed by sheet AND component, never by the key alone: two components of one sheet share a key space by design (a Keycloak realm sheet has `enabled` under every realm), and a flat index had one file's 28 lines claiming 46 rows on a real sheet — half of them offering to open a file with no line for them. A row offers it only when some preview line carries that row's key — a row the file has no line for (a product default) gets no affordance, since one that opens nothing is worse than none. Hidden in print: the printed artifact is the sheet. **`ArtifactPreview.id` identifies one previewed FILE, not one sheet/component**: several previews sharing an id are treated as INSTANCE VARIANTS of the SAME file and rendered as tabs (`mine = previews.filter((a) => a.id === target.id)`, tab strip iff `mine.length > 1`) — right for one template rendered per environment, wrong the moment a sheet/component covers several distinct files (a Terraform module's `main.tf` and `variables.tf`), which would otherwise render as bogus instance tabs of each other. The fix lives entirely in the PRODUCERS, not the viewer: `previewId(sheet, component, file?)` (preview.ts) appends a file discriminator so two files never collide, while omitting `file` (every producer before the Terraform recipe) reproduces today's id byte-for-byte. The viewer needed NO logic change for this, because the row->preview index was already keyed by LINE, not by preview — `artifactIndex` maps `(sheet, component, key) -> id` per line a preview carries, so a row always routes to whichever FILE actually holds its line; the id-collision bug was purely "two unrelated files pretend to be tabs of one," never "a row can't find its file." **`nature: "artifact" | "source"`** (default `"artifact"`) exists because a preview is no longer always "a whole deployed file" — a Terraform module's `.tf` is the AUTHORED source the deployed thing was derived from, never rendered or deployed itself, so the panel's "Rendered from" header would be a false claim over it; `nature: "source"` swaps it for `t.artifactSourceFile` ("Source file") instead. It changes nothing else — not the row->preview index (still line-keyed regardless of nature), not gap counting (`unrendered`/`absent` mean the same thing either way), not review scope — a source preview is simply all-`verbatim` in practice, since there is no substitution engine standing between the authored text and what is shown.
- `src/html/app.ts`'s **`pivotVersions`** + `App`'s `versionPivot` — the columnar comparison an upgrade review actually asks for: one column per VERSION, rows keyed by sheet + path + key, across the whole document rather than per sheet ("what moved between these two releases" is not a per-sheet question, and `enabled` under a realm is not `enabled` under a client). It exists because the component axis could NOT be used: on three of the four sheets such a review needs — user federation, OIDC/SAML clients, and keycloak.conf — that axis is already spent on the data's own identity via `split: { by: name | clientId }` (corp-ldap/partner-ldap, poc-oidc/poc-oidc-batch, the files), and taking it for versions gives up the very breakdown those sheets exist for. The version axis is free AND crosses the component axis rather than competing with it, exactly as `diffview.ts` already merges categories by name. Emits the same `{ components, rows }` shape `pivotSheet` does so `PivotView` renders it unchanged — one columnar table in the product, never two that drift. Read-only (`reviewEnabled=false`, no targets): a cell from the baseline version has no review target in the current document, and the lens/document distinction is the same one `ArtifactPanel` documents. The pivot CELL gained the product default under the value (`defaultLine`), because a version comparison finds most of what it finds among rows that have no value at all — measured, 672 of 1016 rows in one project are unset (`origin: default`/`baseline`) with `value: undefined`, so a values-only columnar view put two blank columns side by side and called it agreement; shown always on an unset row (where the default IS the value in force) and on a set row only when the columns disagree, since repeating an identical default down every row buries the handful that moved. Row agreement counts defaults too — equal values, or no values at all, still differ if the ground under them moved — and the disagreeing default line is marked itself so it cannot be misread as a changed value. **`compare_components: "always"`** (widened from boolean, carried through `providers/project.ts` — and through `assemble.ts`, which collapsed it to a bare `true` when writing the sheet, so for as long as the field existed the viewer never saw it: the declaration parsed, the assembler's own "nothing to compare" check ran, and the sheet still opened stacked with a button offering the reading it does not have) opens a sheet pivoted with no toggle, for a sheet that exists only to compare and therefore has no stacked reading to return to. One fix fell out of building this: the filter menu was gated on `effReviewEnabled`, which diff mode switches off, so entering a comparison removed the only control that reveals unset rows — the rows a version comparison is mostly about. Reviewing is what diff mode disables; choosing which rows are on screen is not reviewing.
- `src/edits.ts` — edits made in a GENERATED document by whoever maintains it afterwards, laid over the sheets before anything else reads them. An edit is an `applied` review item and is APPENDED, never written into the row: the original value stays tied to its `source` (a real line in a real config file, checked by `verify`) and the chain between it and the current value stays readable. The alternative — mutate the row and keep only the newest — was rejected because it makes the document indistinguishable from the spreadsheet it replaces: you can see what the value is, never what it was or when it moved. Only `value` and `remarks` are editable; key/description/default are statements about the PRODUCT, not about this installation, and are not the recipient's to restate. Prose edits carry the language they were written in, so a Japanese note never stands in for a translation nobody made. `applyEdits` returns the input sheets UNCHANGED (same object) when there is nothing to apply, so an unedited document costs nothing and behaves exactly as it did before the feature existed. Added rows (`creates: true`) are DECLARED, not inferred from "the target does not resolve" — that reading would silently resurrect rows a regeneration deliberately removed — and an added row whose category is gone comes back in `orphaned` rather than disappearing. Deleting a row STRIKES IT THROUGH and never removes it — a row that vanishes takes its history and its source map with it and leaves no way to ask what used to be there — and both directions (`deletes: true` / `deletes: false`) are appended, so the state is a fold over the chain rather than a set of deleted keys: striking a row out and restoring it months later are two decisions, and the second is not a correction of the first (unlike an undone typo, which is why `handleUndoEdit` deletes its entry outright)
- `src/edits.ts`'s **`planFromEdits`** + `apply.ts` — an edited sheet returned by its owner IS the review file (`apply -r sheet.html`, read by scanning, no DOM in the CLI), so nothing depends on anyone remembering to export. The history is COLLAPSED to one net change per cell before it goes anywhere near a file: the file still holds the original value, so replaying 500 -> 600 -> 700 step by step fails at the first step the moment part of it was applied by hand, and cascades. The split that follows is the whole point — a value change on a source-mapped row is applied deterministically (located, verified against what the file holds, rewritten), while an added row and a struck-out row cannot be, because where a new setting belongs and whether a removed one is deleted/commented/left-to-default are judgements about the file. Those go to the AI prompt, which is ~2 KB against a ~400 KB document: the HTML itself is never what an AI reads
- `src/html/markdown-runtime.ts` + `src/html/app-md.ts` — the markdown renderer is REGISTERED, not imported, because a static import in app.ts would pull marked (~45 KB on a 145 KB viewer) into every generated file including the many with no document at all. `app-md.ts` is a second entry point — the only module that imports marked — and generate.ts builds from it exactly when a sheet has a document AND editing is on. A document sheet carries its markdown source and its images alongside the rendered html for the same feature: rendering happens at BUILD time, and an image was embedded as a data URI then, so it lives in the html and not in the markdown — re-rendering an edit without the image map drops every picture silently. The html is re-rendered from the edited markdown rather than stored beside it, because storing both lets them disagree and only one of them is a fact somebody typed. A PASTED image goes into the markdown as a content-addressed path and rides on the edit as `assets` — a data URI inline works equally well and reads terribly, and the markdown is exactly what a person is there to read; assets accumulate across the whole history, because a picture pasted in one edit and still referenced by a later one belongs to the later text too. The document sheet carries `source_file` (a document sheet takes an early exit in assembleSheets and used to lose it), without which apply can report the rewrite but never say what to rewrite
- `src/html/app.ts`'s **`getStorageKey`** — unsaved edits live in localStorage until the file is written, and the key says WHICH document they belong to. The metadata (project/version/generated_at) cannot say it: every copy of one generated file carries the same, so two copies shared a buffer — edit one without saving, open another, and the first one's work is in it ready to be saved into the wrong file. Each save stamps a revision id (SaveRecord.id) and the key carries the newest one; a file never saved has none and keeps the bare key, which is what a freshly generated document always used. The superseded revision's buffer is removed on save, or reopening an older copy would offer work that has already gone into a newer file. Only the UNSAVED work goes in there (`savedReviews` minus `persistedIds`): writing the whole history back would duplicate the file into the browser and make "what is unsaved" unanswerable from the buffer alone. Previous-session work is always LOADED, never offered: a restore/discard dialog was built and removed, because a discard button is an irreversible action sitting beside the safe one, and a "later" answer lets two working states exist at once — put the work aside, edit, and there are two sets of unsaved changes and a question about which one the file gets. One state, always loaded; what remains is to SAY the screen is not what the file says, which the overview does (count, list, and how much came from this browser)
- `src/html/save.ts` — the page rewriting itself. The pristine markup is captured before the first render, and saving is that string with one `<script>` block SPLICED (two `indexOf` calls, no parse). It went through DOMParser first, on the grounds that a `</script>` in the data could cut the document in half — but that cannot happen, because `embedJson` escapes every `<`, and the exact opening tag emitted by generate.ts is what is matched, so there are no reordered attributes either. What the parse DID do was freeze the page for hundreds of ms on a real sheet, before the save dialog could even open. Two more ordering rules keep saving responsive: the file picker is asked for BEFORE the document is built (it needs the user gesture, and it is the part that must not wait), and a paint is forced after setting the busy state or it never reaches the screen. A dismissed picker is NOT an error and must not fall through to a download nobody asked for — that is how an edit ends up in the Downloads folder and is lost the next time the original is opened. The block holds `{ reviews, saves }`; a bare array (what the first version wrote) is still read, because dropping those entries is the exact failure the feature exists to prevent
- `src/html/i18n.ts` — i18n message definitions (ja/en)
- `src/html/styles.ts` — all CSS as a template string
- `src/prompt.ts` — framework-free model types + source-map resolution + English AI-prompt builder (shared by the browser app and the CLI)
- `src/apply.ts` — deterministic, verified apply core (source map → edits; injected file I/O); held items fall back to the AI prompt
- `src/verify.ts` — source-map verification core (checks each value's source resolves in the real files; injected file I/O). A check that succeeded only because the line+anchor fallback rescued an unresolved structural `path` carries `fallback` and is counted in `VerifyOutcome.fallback` — still `ok` (the value IS there, so no gate should fail), but reported as `OK~` / `line-fallback` and never hidden by `--quiet`, because "resolved by path" and "the path is broken and the line happened to match" are different claims and only the first survives a reordering. The `isDefault` short-circuit (`collectValues`' `ValueEntry.isDefault`, `origin: "default"`) only fires when the row ALSO has no `source` — the documented-default case, which genuinely has nothing to resolve. A `default` row that DOES carry a source (the widened definition: a value observed in a generated artifact, see `types.ts`'s `Origin` comment) falls through and is verified exactly like any other row instead of being counted as `default` and skipped — the short-circuit used to be safe unconditionally only because a `default` row never had a source before `SheetInputs.authoredKeys` (`assemble.ts`) started producing ones that do, and skipping those would have silently stopped checking every source map a recipe demoted from `overlay`
- `src/line-config.ts`'s **`LineConfig.bareFlag`** — a directive with NO argument is a setting whose value is its own presence (`rtcsync` in chrony.conf, sshd's bare keywords): the file says the thing by naming it and says nothing by leaving it out. Set for `space` and deliberately for NOTHING else — that is meaning, not caution: in a `key=value` format a line with no delimiter is prose, a typo, or a file this parser was never meant to read, and `generic` is the priority -100 fallback that matches every file there is, so inventing rows there would turn a README into a sheet. Before this, `extractLines`' `if (value === "") continue` dropped such a line and reported nothing — the row simply never existed, which is the one failure this project refuses to leave silent. The value is a STRING (`"true"`) rather than a boolean because every consumer downstream — the sheet cell, a review's `current`, a dictionary `default` — is text. Two things follow from the value being nowhere in the file, and both are why `lineLocate`/`lineEdit` could not simply be reused: `locateLine`'s ordinary test is "the line still carries the current value", which for a flag can never pass, so the flag-aware path substitutes an EXACT whole-line match against the anchor (`rtcsync` must not resolve against `rtcsyncfoo`, which a substring test would accept); and `edit` REFUSES, because turning a flag off means DELETING its line and turning one on means inventing a position for a line the file does not have — neither is the literal current->suggested replacement `lineEdit` performs. Refusing is not a dead end: `computeApply` turns a parser's `edit` error into a HELD change carrying that reason, the same path a `substituted` row takes, so the change reaches the AI prompt for a human instead of being dropped or guessed at. `lineLocateFor(cfg)`/`lineEditFor(cfg)` are factories rather than an extra parameter on `lineLocate`/`lineEdit`, because `ConfigParser.locate`'s fourth argument is already `ExtractOptions` — widening that position would typecheck clean at `locate: lineLocate` and hand the function an options object where it expected a flag value at runtime.
- `src/parser.ts`'s **`parserForSource`** + **`SourceLocation.baseFormat`** (types.ts and prompt.ts both carry it) — the parser a recorded location must be READ BACK with, which detection alone cannot answer. A format only ever has to be DECLARED (`templates[].format`, `static_files[].format`) when the file name cannot say it, and `space` is never detected at all by design — so a row written by the declared parser was being read back by whatever the extension selected. Invisible for an ordinary `key value` row (every line parser locates it identically by anchor + value) and fatal for a presence flag, whose value is nowhere on its line: measured on a real project, `rtcsync` extracted correctly and then failed verify with "anchor not found with the current value". The recipe stamps `spec.format` — the DECLARED one only, never the inferred one, or every source of every project would carry a copy of what its filename already says — onto each source, and verify/apply resolve through `parserForSource` instead of `resolveParser`. Its two shapes are decided by `ConfigParser.wrapsBaseFormat` (jinja2 alone): a template parser is KEPT and told the base format to delegate to, since replacing it would read the raw `{{ }}` template as if it were a config, while any other parser is replaced outright. `parsers/jinja2.ts`'s `locate`/`edit` gained the same `opts.baseFormat` preference its `extract` already had — its no-path branch used to fall back to the `generic` parser unconditionally, which is right only while no base format was declared.
- `src/structural.ts` — path-based structural edit/locate for YAML & JSON (surgical, format-preserving; via the `yaml` lib). Paths address maps by key and lists by identity predicate (`services[name=web].port`) or index, so resolution survives reordering. For structured files apply/verify resolve by path FIRST (line+anchor is the fallback); `structuredFormat()` routes yaml/json here and xml to `xml.ts`
- `src/xml.ts` — XML support (via `saxes`): extract element-text/attribute values and surgically edit/locate them by a stable path (`server.connector.@port`, `services.service[name=web].port`). Repeated elements addressed by identity attribute → reorder-robust
- `src/toml.ts` — TOML support (line scan, no extra dependency): `[table]`→nested path, `[[array-of-tables]]`→identity predicate (`service[name=web].replicas`) or index; scalar values only. Same index/locate/edit shape as `xml.ts`
- `src/systemd.ts` — systemd unit support (line scan): `[Section]`+`Key=Value`, repeated keys indexed (`Service.ExecStartPre[1]`, unique param key). Same index/locate/edit shape
- `src/shell.ts` — shell script support (line scan + a quote-aware tokenizer): extracts ONLY the two unambiguous shapes a wrapper script carries reviewable values in — a statement-initial `NAME=value` assignment and a long option with a value (`--region r` / `--region=r`) — keyed by the variable name or by the option WITH its dashes so the two can never collide, repeats indexed. Skips heredoc bodies (payload, not configuration), command substitutions (`$(…)` is a command whose output becomes the value, not a literal), bare flags and short options (`-rf` is indistinguishable from a bundle). `isShell(file, content)` detects it by extension or shebang. Its point is `*.sh.j2`: jinja2 strips `.j2` before resolving the base format, so a templated CLI wrapper's `--secret-id {{ kc_db_secret_name }}` records its templateVar and resolves against the role's variable file
- `src/nginx.ts` — nginx support (char scanner → block tree): directives + `{}` blocks; labeled blocks addressed by label (`http.server.location[/api].proxy_pass`, reorder-robust), repeats indexed. `isNginx(file, content)` detects it (no reliable extension); used by extract/apply/verify
- `src/httpd.ts` — Apache httpd support (line scan → block tree): `Directive args` + `<Tag>…</Tag>` containers by label (`VirtualHost[*:80].DocumentRoot`). `isHttpd(file, content)` detects it — by filename (httpd.conf/apache2.conf/.htaccess), by a `<Tag>` block, or (P10, `looksLikeHttpdDirectives`) by content alone for a bare `*.conf` with no `<Tag>` at all: the RHEL `conf.d/*.conf` layout is one directive-only fragment per module/vhost, so `httpd.conf` + `conf.d/proxy.conf` in the same `import -f` used to extract the first and silently contribute nothing from the second (misdetected as `sysctl`, which found no `=` to extract). The signal is vocabulary shape — Apache directives are `CamelCase value` (no `=`), sysctl/ini are `key = value` — and it requires directive-shaped lines to OUTNUMBER assignment-shaped ones (never a single line) and only ever applies to `.conf`, never an extensionless file, to keep the blast radius small; checked against every file in `examples/` and a real downstream project for an unchanged parser selection before shipping
- `src/hcl.ts` — HCL (Terraform / Consul / Nomad / Vault / Packer) support (char scanner -> block tree, labels as path segments so reordering resources does not break a source map). `hclIndex` emits only attributes it can VALUE: an interpolation, a reference or an expression is skipped, and rightly — `"app-${var.environment}-"` is not a value, and a row claiming it as one would be lying. `hclAttributeSites(content)` is the SAME walk reporting every attribute's path and line regardless, for anything that needs to know WHERE an attribute is written rather than what it says. One walk, two consumers, deliberately: the block-path logic decides row identity and a second copy would drift. The split matters because the two questions look alike and are not — measured on one project's five Terraform modules, 140 attributes assigned and 47 valued, so the preview bridge (recipes/terraform-plan.ts) asking the index for positions found under a third of each file and one whole module, every argument of it a `var.` reference, none of it at all
- `src/haproxy.ts` — HAProxy support (line scan → sections): named sections + directives, repeated directive by first arg (`backend[app].server[web1]`). `isHaproxy(file, content)` detects it. nginx/httpd/haproxy all content-detected because `.conf`/`.cfg` collide with sysctl/ini
- `src/registry.ts` — `sharedRegistry(name)`: the backing array for all three plugin registries (`parser.ts` / `recipe.ts` / `metadata.ts`), keyed off `Symbol.for` so it is process-wide. A plugin's `import { registerParser } from "review-sheet"` resolves from the PLUGIN's location, so when the CLI runs from a different checkout the plugin loads a second copy of `parser.ts`; module identity is by resolved path, so a module-scope array made registration a silent no-op. Only effective when BOTH copies have this — an older `node_modules/review-sheet` still registers into its own array. There is no longer any process-wide mutable *configuration* in this package — only registration goes through `sharedRegistry`; a setting (extraction options, the annotation marker) is threaded as an ordinary argument (`ExtractOptions`, see `parser.ts`) all the way to the call that needs it
- `src/parser.ts` — the `ConfigParser` interface (detect / extract / locate / edit) + `ParserMeta` type + registry (`registerParser`, `resolveParser`, `getParser`, `listParsers`). The core (extract/apply/verify) dispatches through this — NO per-format `if` chains. `ExtractOptions` (`idFields?`, `marker?`) is `extract()`'s optional third argument — configuration threaded as data instead of read from process-wide state; `extract(content, file)`, two arguments, still satisfies the type (TS allows fewer declared params), so a custom parser predating this type is unaffected
- `src/parsers/*.ts` — one `ConfigParser` per format (line, yamljson, xml, toml, systemd, nginx, httpd, haproxy), each wrapping its engine and self-registering at load; `parsers/index.ts` imports them all. Content-detected parsers (nginx/httpd/haproxy) use high priority; `generic` line parser is the lowest-priority fallback. The jinja2 parser's `locate` DELEGATES to the base format (masking the template first, restoring the returned value, and re-masking `source.path` so it matches the index built over `masked` — `maskJinja` exports the forward `mask` for exactly that round trip) whenever the row carries a structural path, falling back to line+anchor only without one. This is what makes a SYNTHESISED value verifiable: a logrotate flag's value is `true` because the directive is present, and no search of the text for "true" can confirm it, while asking logrotate's own locate for the block's `missingok` confirms it exactly. `edit` is deliberately NOT delegated — masking does not preserve column offsets, so an edit computed against `masked` cannot be written back. Custom parsers register the same way (CLI `--parsers-dir` / auto `./.review-sheet/parsers/`)
- `src/parser-docs.ts` — pure renderers for per-format documentation pages (from `ParserMeta` on each parser); no fs imports; called from CLI (`parsers` command) and gen-docs script
- `scripts/gen-docs.ts` — writes `skills/review-sheet/formats/<name>.md` per parser + injects index/table into SKILL.md and README.md between `<!-- parsers:start -->`/`<!-- parsers:end -->` markers; run with `bun run docs`. Format docs are generated from each parser's `meta` field (see `skills/review-sheet/formats/`)
- `src/extract.ts` — `extractFile(content, file, format?, opts?: ExtractOptions)` = `getParser(format) ?? resolveParser(file, content)` → `parser.extract(content, file, opts)`; plus `buildInput(files, opts?)` and the YAML/JSON engine `extractTree(content, opts?)`. `buildInputWithReport(files, opts?)` is the same build, plus a `BuildReport` (`{ files: { file, parser?, count }[] }`) naming which parser EVERY file resolved to and how many entries it produced — `buildInput` is now a thin wrapper that discards the report (same relationship as `assembleSheets`/`assembleSheetsWithReport`). This exists because `buildInput`'s per-file `continue` on zero entries used to be silent the moment at least one OTHER file in the same call produced something: mixing a working `httpd.conf` with a misdetected `proxy.conf` reported "Extracted 12 parameter(s) from 2 file(s)" with no sign the second file contributed nothing (P10 bug 1) — the CLI's `import -f` now reads the report and warns, by file AND by resolved parser name, for every zero-count file (not an error: a file that is legitimately all comments is not a mistake, but which parser was tried must never be silent, so a genuine misdetection is fixable with `--format`). Source-map extraction is exported from `index.ts` for conversion scripts. `opts.idFields` extends the list of field names that identify a list-of-maps item (built-ins: name/id/key), tried FIRST so an explicit statement about the project's data beats the generic guess — without it Keycloak's `clientId`-keyed clients fall back to a positional `clients[0]`. Threaded as data, spec → `assembleFromSpecWithReport` builds `RecipeIO.extractOptions` (from `build.yml`'s `id_fields`) → a recipe passes it to every `extractFile()` call it makes → `getRecipe`/`resolveParser` need no global; the CLI's `import -f` path passes the same `ExtractOptions` explicitly built from `--id-fields`/`--annotation-marker`. `ExtractOptions.marker` (parser.ts) travels the same way all the way to `locate`/`edit`, not just `extract` — `ConfigParser.locate`/`.edit` both take the same optional `opts` last, so `verifySources`/apply's core pass it straight through and the ts/py annotation parsers' `annotationLocate`/`annotationEdit` read `opts?.marker` instead of any process-wide state; a parser predating `ExtractOptions` (fewer declared params) is unaffected, since TS allows an implementation with fewer parameters than its declared type
- `src/diff.ts` — pure diff between two snapshots → status model (per sheet/category/param, and per-instance value cells for Pattern B); used for summaries/tests. `alignValues()` owns the value-cell pairing and is shared with `diffview.ts` so the CLI and the Compare overlay can never disagree: a row that is Pattern A on one side and Pattern B on the other is compared by expanding the shared value across the other side's instances (that is exactly what `origin: common` asserts), so an equivalent row reads `unchanged` instead of every cell coming out added/removed — which is what makes diffing two DIFFERENT sheets (old platform vs new, during a staged migration) an equivalence check rather than noise
- `src/diff.ts`'s **`ParamChangeKind`** (`value` | `default` | `doc`) and `DiffResult.summary.docOnly` — WHICH kind of thing changed about a row, because "changed" alone is unusable for the comparison people actually run. Measured on a real Keycloak 19.0.2 -> 26.7.0 comparison of ONE unchanged configuration: 67-74% of shared dictionary keys differ in description text, and most of that is not the product moving — of 115 differing realm entries, 32 are a Japanese translation the newer dictionary carries and the older lacks, and 20 are a description the newer one LOST (extraction quality, not product history). Counted as one number, the sign-off reads "115 changed" when nothing configured has moved; the one row that mattered in that comparison — `useTruststoreSpi`, whose PRODUCT default went `ldapsOnly` -> `always` beneath a value nobody touched — sat in the same undifferentiated count as four translation diffs. `default` is therefore classified with the findings and NOT with the prose, and split again by whether anything was holding it back — `effective` when the row is unset (`origin: default`, or `baseline`, which says the vendor shipped the directive and this file dropped it, leaving the product built-in to govern: MORE exposed, not less) and plain `default` when the project sets a value that still wins. A materialized row carries no value at all (all 668 `origin: default` rows in the project measured have `value: undefined`), so a moved default changes nothing else about it and, undifferentiated, reads exactly like the harmless case: the documented default moving is a statement about the deployment even when every value held still, and it is rare enough (2 of 171 realm keys, 1 of 30 LDAP, 0 of 117 client) that burying it is the whole risk. `status` keeps its original meaning — "changed" still covers every kind, so every consumer that predates this reads the same number it always did — and `changed: ParamChangeKind[]` says which kinds, empty for added/removed/unchanged because a row present on one side differs in PRESENCE, which `status` already states. `summary.docOnly` is the subset of `changed` that is nothing but prose, reported rather than hidden (dictionary churn is real information about the dictionaries, just not about the deployment) and printed by the CLI as `6 changed (4 description/remarks only)`. Note one thing this does NOT fix: `diffParam` compares `description`/`remarks` through `pickLang(..., "en")`, so a ja-only wording change is invisible to the diff entirely — orthogonal to this split, and worth closing when the per-column description view lands.
- `src/diffview.ts` — pure builder for the Compare *overlay*: merges two versions into render-ready sheets (union, removed kept in place) + synthetic reviews (changed values as old→new) + a status map. The viewer renders this through the normal ParamTable, so Compare keeps the real sheet look (tabs/freeze/outline/search), not a separate diff layout
- `src/types.ts` — public type definitions (input model incl. `SourceLocation`, review schema, options). `Origin` is a WHO-DECIDED taxonomy (project, per-env / project, shared / project, baked-in / the product), not an evidence-channel one — and `default` was widened to cover two evidence channels that both mean "not us": the documented default (no `source`) and a value OBSERVED in a generated artifact (`source.generated: true` — a Terraform plan's `change.after` reports a value the author wrote and one the provider defaulted IDENTICALLY, with no way to tell them apart from the plan alone; the provider decided, so it's `default`, exactly like a materialized row). Deliberately not a fifth `Origin` value: `SourceLocation.generated` already says "observed, not authored", and a new enum member would only restate what that field says, the same reasoning `embedded`/`default`'s split from a bare boolean never needed. The invariant that makes the merge safe is the one thing checked in code, not prose: a `default` row never carries a location in a file we author — no `source`, or a `source` with `generated: true` — enforced by `validate.ts`'s `findDefaultOriginErrors`, the cross-field twin of `findEmbeddedOriginErrors`. `baseline` (the ansible recipe's `baseline:` — see its own entry below) DOES earn the fifth `Origin` value the generated-artifact case above deliberately did not, because the two situations differ in the one way that matters: the generated-artifact `default` row has the SAME decider as every other `default` (the product) and differs only in which evidence channel observed it, so a second enum value would restate what `source.generated` already says; `baseline` has a DIFFERENT decider (the distribution's packager, not the product) and a different meaning for the row (the value is not merely undeclared by us, it is not in effect ANYWHERE — no line of the deployed artifact holds it). It gets the same `source`-less invariant `default` does, checked by `validate.ts`'s `findBaselineOriginErrors`, but with no evidence-channel exception: a `baseline` row's absence from our files is the whole fact, never one of two ways of expressing it. `ParameterBase.baseline` (a plain string, not an `Origin`) is the separate, more common case: a row we DO have, carrying the vendor's original value beside our current one for comparison — that field answers "what did the distribution ship", never "what does the product document" (`default`), and the two measurably differ (httpd's own docs say `ServerRoot` defaults to `/usr/local/apache`; RHEL's package compiles in `/etc/httpd`). Shown in ONE column with `default`, never two: they are two SOURCES for the single question a reviewer has — what does a freshly installed host do here — and a column each put the tool's own plumbing on screen instead of the answer; the shipped value wins because it is what the host has. On a `baseline` ROW that column shows what the vendor had and deliberately not what applies instead, since the container may have been commented out along with the directive and answering that needs the product's own merge semantics, which this tool does not model The baseline is read with the parser the DEPLOYED path resolves to, not the one its own filename suggests: a pinned vendor copy is named for its package NVR (`httpd.conf@httpd-2.4.37-43.module+el8…`), which no format detection recognises — it fell through to the generic key=value parser and produced ZERO entries, and `formatOf` cannot help because it only answers for STRUCTURED formats. The zero-overlap warning caught it immediately and called it "almost certainly the wrong file", which was half right: the right file, read the wrong way.
- **`ParamOption`** (types.ts) and the `options` field on it, `DictionaryParam`, `MetadataResult`, `Parameter`, `ParamData` — a stored value and a displayed value are not always the same string. Keycloak's LDAP search scope is written `1` or `2` through the API and shown as "One Level" / "Subtree" in the admin console, so a reviewer who only ever configured it through that console meets a bare `1` in the sheet and has no way to judge it. Two things follow from where the label comes from. It is the PRODUCT's, so it is localized by the product and carried as `LangText` — and often only in English, because a product translates its field labels long before its option lists (measured on one release: `oneLevel`/`subtree` present in `en`, absent in `ja`, while `searchScope` itself was translated); `pickLang`'s cross-language fallback is exactly right for that, and showing the English name beats showing nothing, which is what a bare code already was. And it is a product fact, so it is extraction-owned: an overlay may not set it, since a community guess at which values are legal is indistinguishable from the product's own list. **First-class on `Parameter`, deliberately not an `extra` entry**: `fillExtra` (enrich.ts) takes a `string` and `extra` is baked at generate time — the same reason `formatProvenance` renders provenance down to a static string there — so a label routed through `extra` could never follow the viewer's language toggle the way `description` and `remarks` do. `localizeParam` resolves each option's label and never touches its `value`. The viewer's rule is the load-bearing one: `optionLabel(param, value)` returns the product's name for the value CURRENTLY shown, and `ReviewableCell` renders it as a separate `valueLabel` slot beside the value — **never concatenated into it**, because `value` is the same string the review dialog opens with, the copy button yields and `apply` writes back, so `1 (One Level)` reaching it would put that text into a deployed configuration file (`tests/viewer.test.ts`'s "never folds the label into the value" is that guarantee). Dropped while a suggestion is on screen (the label describes the current value, and leaving it between a struck-through old value and a new one reads as if it belonged to the suggestion), and shown on the DEFAULT column too, since an unset row is judged by what applies to it. A value no option lists gets no annotation at all rather than a guess — a bound dictionary is pinned to one product version and a deployment may run another, and a value may be a `${env}` placeholder. `label` is optional so the same field carries the other half of what an enumerated setting knows: its LEGAL VALUES for a product that lists them without naming them (PostgreSQL's `pg_settings.enumvals`), which two dictionaries had been folding into the end of the description as prose — an edit to the product's own words that this field exists to stop.
- `src/schema-errors.ts` — `suggestNearest` + `formatAjvErrors`, and a LEAF: it imports nothing from this package, so any module may use it without a cycle. That is the whole reason it exists. Three modules had grown their own copy of the same Levenshtein, each carrying a comment naming the cycle it was avoiding (`assemble.ts` imports `findDictionary` from `providers/dictionary.ts`, so dictionary.ts could not import back; `spec.ts` reached up into assemble.ts for it) — a leaf is what those comments were describing the absence of. `assemble.ts` re-exports `suggestNearest` so importers that reached for it there keep working. `extract.ts` deliberately keeps its own: its threshold is `length / 3` rather than `length / 4`, so folding it in would change which suggestions the extraction layer makes — a behaviour decision, not duplication. `formatAjvErrors` requires its caller's Ajv to be built `verbose: true`, because an `additionalProperties` error only carries `parentSchema` — the schema that rejected the field, hence the list of names it DOES accept — when verbose is on; that list is what makes a "did you mean" hint possible without every throw site hand-maintaining its own copy of "what fields does this object take".
- `src/schema/dictionary.schema.json` + `parseDictionary`'s validation — the dictionary was the ONE input this tool read without validating: three `typeof`s and a cast (`product`/`version`/`parameters`), everything else waved through. A misspelled field was therefore a SILENT no-op — the value never arrived, the row rendered with no default or no group, and the strict-metadata gate blamed the project for not writing a description the dictionary was in fact supplying under a typo'd key. Every other input (`build.yml` via `spec.ts`, an overlay via `parseOverlay`, the model via `validate.ts`) was already schema-checked or hand-checked; this was the gap, and it is the input a project is most likely to hand-edit or receive from elsewhere. A HARD error, matching build.yml and the overlay: there is no warning channel here, and a rejected field is loud and immediately fixable. Two rules in it are worth naming. **`kind: container` must not carry a `default`** — a container holds other objects and has no value of its own, so what looks like its default is the empty shape of what it HOLDS (`{"policies": []}`), which is an object where the field may only be a scalar and which `resolve()` would hand out through `String()` as `[object Object]`; that was live in three shipped dictionaries and surfaced only because materialize happens to skip containers, an accident of ordering rather than a guard. **`parameters` must not be empty** — an extraction that produced nothing is the same failure as a rule that matched nothing, which this project reports everywhere else. The schema's `langText` closes the other half of a real hole: `description: { enn: "..." }` used to pass every check and then fill NEITHER language. The overlay is not covered by this schema (it is parsed by `parseOverlay`, whose error messages are better — they say WHY a field is refused, not just that it is), so the same language-key check is duplicated there by hand; that duplication is the deliberate half of the split. Field names are pinned in three places at once and cannot drift: `DICTIONARY_PARAM_FIELDS`/`DICTIONARY_DOC_FIELDS` (providers/dictionary.ts) carry `Exclude<>` assertions that fail to COMPILE against the TypeScript types, and `tests/dictionary-schema.test.ts` compares the same lists to the schema's own `properties`. `since`/`until` were dropped from `DictionaryParam` rather than schema'd: typed, read by nothing, used by no dictionary — blessing them on the first day of `additionalProperties: false` would have been the silent-no-op this file exists to remove.
- `src/validate.ts` — ajv schema validation, plus three cross-field rules the schema can't express, all walking the assembled tree the same way: `findEmbeddedOriginErrors` (an `embedded` param can't carry per-environment `instances` — a literal baked into the source is never per-environment), `findDefaultOriginErrors` (a `default` param's `source` — or, for Pattern B, any instance's `source` — must have `generated: true` if present at all; see `types.ts`'s widened `Origin` comment for why), and `findBaselineOriginErrors` (a `baseline` param's `source` must be ABSENT, full stop — no evidence-channel exception, since a `baseline` row's absence from our files is the whole fact; see `types.ts`'s `Origin` comment for why it is a fifth value where the generated-artifact `default` case was not). All three collect every offender before throwing, same "name them all at once" discipline as `assemble.ts`'s `missingCategory`/`ghostCategories`
- `src/cli.ts` — CLI entry point (import / generate / validate / verify / apply / serve). `diff -i base.json -i current.json` prints what changed between two snapshots (the reviewed revision's input.json vs now — the "what still needs review" question, answered from VCS rather than from a per-row ledger). `serve` runs a `Bun.serve` on 127.0.0.1 exposing `POST /api/apply` (computeApply → optional write) and `/api/verify`; the embedded app (generated with `server:true`) calls them so reviewers apply edits straight to local files. The apply/verify cores are reused unchanged (pure, injected I/O)
- `src/metadata.ts` — the `MetadataProvider` interface (`resolve(query, ctx)`) + `ParameterSheetInput`-independent registry (`registerMetadataProvider`, `resolveMetadata`, `getMetadataProvider`, `listMetadataProviders`), mirroring `parser.ts` (array registry, replace-by-name, priority sort at resolve). `MetadataQuery.binding` carries the ALREADY-RESOLVED `bind.ts` `Binding` for this key (or `undefined` — most keys have none), run once per build before any provider sees the query; no provider re-derives it. `MetadataQuery.variable` carries a row's ORIGINAL extracted identity when `assemble.ts`'s `keyMap` renamed it to a product key (e.g. Ansible's `kc_hostname` filed as `hostname`) — a fallback for a native channel keyed by the variable name, not the row's current display key (`argument-specs.ts` is the one provider that reads it; see its own entry below). Built from `assemble.ts`'s per-`Draft` `variable` and handed to `enrich()` as `EnrichOptions.variables` (sheet → row key → variable), independent of whether the project declared an `under_key` display column for it. `description`/`remarks` are `LangText` (`string | { en, ja }`, defined + `pickLang`ed in `types.ts`): providers carry the full map through **unresolved** (no per-lang collapse), so the browser viewer can switch languages at display time. `resolveMetadata` merges providers in priority order (project 100 → argument-specs/terraform-variables 50 → dictionary 30), but the two `LangText` fields (`description`/`remarks`) merge PER LANGUAGE KEY, not field-wise first-wins like every other field: this is what lets `en` come from the value's own native channel (Terraform's `description = "..."`, Ansible's argument_specs `description:`) while `ja` comes from `sheet.yml`, without either duplicating the other. A plain `string` result (what a native channel returns) claims and locks the WHOLE field the moment it lands on an empty slot — there is no "other language" to merge into a language-agnostic string — while a `{ en?, ja? }` object only fills the keys still open; `MetadataContext.nativeLang` (`"en" | "ja"`, default `"en"`, `build.yml`'s `enrich.native_lang` / CLI `--native-lang`) is what tells a native-channel provider which language its own plain string IS, via `nativeLangText()`, so it can hand `resolveMetadata` a properly-tagged `{ [nativeLang]: text }` instead of a bare string that would wrongly lock the field for every language at once. `Provenance` is widened to `LangProvenance = Provenance | { en?; ja? }` — the same per-language shape `LangText` already has, because a description's two languages can genuinely trace to two different sources. `resolveMetadata` now credits provenance PER LANGUAGE KEY: `mergeLangField` reports back WHICH language keys it actually filled (not just whether it contributed), and `provByLang[lang]` is set from whichever provider's result filled that slot — replacing the old "the provider that filled the field's FIRST language key wins the whole field" approximation, which was simply wrong the instant two providers split a description (verified: it was already wrong for a SHIPPED example, `examples/ansible-httpd`'s `ServerTokens`/`MaxRequestWorkers` — `argument-specs.ts` supplies `en`, the `httpd@2.4` dictionary supplies `ja` via the still-open-slot fill `mergeLangField` documents — even though the migration design this task implements predicted no shipped example would move). `collapseProvenance` (also used by `providers/dictionary.ts`, see its own entry) reduces a uniform, or single-language, per-language pair back to the bare scalar before it reaches `ResolvedMetadata.provenance`, which is what keeps every provider/dictionary that has never actually split a description byte-identical to its pre-`LangProvenance` output. `provenanceForLang` is this module's own SINGLE-layer lookup (one provider's own result, scalar-or-map, no document-level fallback) — distinct from `providers/dictionary.ts`'s `provenanceFor`, a separate 4-tier resolution (entry map → entry scalar → doc map → doc scalar → `"community"`) that only the dictionary provider needs; both are deliberately NOT `pickLang` — `pickLang`'s cross-language fallback is right for prose (show something) and wrong for a trust claim (a Japanese translation's origin is never answered by the English text's origin next to it)
- `src/providers/*.ts` — one `MetadataProvider` per source (project, argument-specs, terraform-variables, dictionary), self-registering at load like `src/parsers/*.ts`; `providers/index.ts` imports them all, then snapshots the just-registered names as `BUILT_IN_PROVIDER_NAMES` — the one place "what counts as a built-in" is derived instead of hand-copied (six test files used to keep their own hard-coded allowlist for stubbing out non-built-in providers between tests; adding a provider and forgetting one copy made it silently no-op depending on test run order — see `tests/only-builtin-providers.ts` for the single surviving copy). `project.ts` reads the project's own metadata file (`sheet.yml`, wins every field it sets, provenance `project`; also the sole source of a param's `category` and `dict_key`, both read directly rather than through `resolve()` — see `bind.ts`). `ProjectMetaDoc` is `{ params?, categories?, under_key? } | { sheets? }` — flat `params:`/`categories:`/`under_key:` (a single spec-wide table plus that one sheet's display config) for a single-sheet spec / `import -f --project`, or `sheets: { <sheet name>: { params:, categories:, under_key: } }` for a multi-sheet one; `loadProjectMeta` rejects a file setting both top-level and `sheets:` (no flat fallback under `sheets:` — see below for why), and `paramsForSheet`/`categoriesForSheet`/`underKeyForSheet`(doc, sheet) are the one place either shape is read: a `sheets:` doc returns ONLY that sheet's own value (an unnamed/unknown sheet gets `{}`/`[]`/`undefined`, never another sheet's), a flat doc returns the same value regardless of `sheet`. This is what closes a real leakage bug: with flat `params:`, two sheets sharing an extraction source (e.g. two Ansible roles reading the same group_vars file) share a key's category/description too, so a key that leaks from one sheet's drafts into another's (a missing `exclude:` filter, a renamed variable) can borrow the WRONG sheet's documentation and file in looking legitimate, no error — `sheets:` makes that key resolve against a namespace that never declared it, so the ordinary "no category"/"no description" strict gates name it instead. `categories`/`under_key` (P7) — a sheet's top-level tab display order and the ansible recipe's under_key column label — moved here from build.yml: both are display facts about how a sheet is READ, the same kind of fact `category:`/`out_of_scope:` already are, not about where its data comes from; splitting the assignment (sheet.yml) from the tab order (build.yml) let a second, easy-to-forget write silently produce a "ghost tab" (a category nobody declared showing up with no error, no warning — verified: `verify: 2 ok, 0 warn, 0 error` / `tabs: ['General', 'Generl']` for a single typo'd `category: Generl`). `groupByForSheet` reads a sheet's `group_by: file` — group a row the project does not categorise by the FILE it belongs to, which is how an incumbent paper parameter sheet is organised and the only workable answer where a dictionary's own `group` is a bad review split (httpd's is the Apache MODULE, so it collapses General/KeepAlive/Logging into one "core" tab). Which file is DECIDED, in `fileCategory`: sourced from the template, or carrying an `under_key` variable, or having no source at all (a product default of that artifact) -> the artifact; anything else -> its own file. That last arm is load-bearing — `keycloak_dist_src` tells the role where to download the distribution, is not a line of keycloak.conf, and filing it there makes the sheet claim something false about the file. `checkProjectMetaSheets(doc, knownSheets)` fails the build if `sheets:` names a sheet the build has no `SheetInputs` for (same discipline as `assemble.ts`'s `dictionaries` sheet-name check); `declaredComponentsForSheet` is the same two-way check one level down — a `components:` block for a component the sheet produced no rows for, which the unused-PARAM check structurally cannot catch, because a dead block is normally a copy of a sibling sheet's and every key in it exists on this sheet under a different component. Measured on a real spec: two sheets each carried the other's block, 90 lines applying to nothing, and every gate passed. `argument-specs.ts` reads Ansible `meta/argument_specs.yml` and `terraform-variables.ts` reads Terraform `variable "x" { description = ... }` blocks (via `extractFile()` — no bespoke HCL parsing), both provenance `community`, same priority (the ecosystem's own metadata channel for the value next door, authored by whoever wrote the role/module); NEITHER is sheet-scoped the way `project.ts` now is — a spec-wide list, read the same regardless of which sheet is asking — a narrower, currently-unaddressed instance of the same class of leakage. `argument-specs.ts` matches `query.key` first, falling back to `query.variable` (see `metadata.ts`) when the two differ and the first miss — so a role's own variable-keyed entry (`kc_hostname`) stays reachable for a row `keyMap` renamed to the product's key (`hostname`) instead of going permanently dead the moment the rename happens; `terraform-variables.ts` has no such fallback (Terraform variables are never renamed by a recipe the way `keyMap` renames an Ansible variable, so there is nothing for it to fall back from). Both wrap their plain-string `description` as `{ [nativeLang]: text }` (`nativeLangText()`, `MetadataContext.nativeLang`) rather than returning a bare string, since a native channel's text is written in ONE language and a bare string would tell `resolveMetadata`'s per-language merge "this speaks for every language at once" (see `metadata.ts`); `dictionary.ts` is a plain lookup off `query.binding` — no key matching or file access of its own (see `bind.ts`) — returning `entry.description`/`default`/`type`/`scope`/`docs_url`/provenance for the already-resolved `DictionaryParam`; `DictionaryDoc.provenance`/`DictionaryParam.provenance` are `LangProvenance` (metadata.ts) — a document can carry `{ en: official, ja: community }` once (nginx/httpd: hand-transcribed English, this repo's own Japanese translation) instead of forcing a per-entry override onto every one of its parameters, and an entry can override just one language over that default (Keycloak's `db`: no entry override for `en`, so it falls through to the document's `extracted`; `ja` is entry-level `community` — a hand-written translation the product never shipped, which the OLD single-scalar `provenance` field could not help but credit as `extracted` too). `provenanceFor(lang, entryProv, docProv)` resolves ONE language through four tiers, each checked in full before falling to the next — entry map's key -> entry scalar -> doc map's key -> doc scalar -> `"community"` — and deliberately does NOT fall back to the SAME map's other language key the way `pickLang` (types.ts) would: `pickLang`'s cross-language fallback exists to put SOME prose on screen, which is right for `description`/`remarks`, but wrong for a trust claim — the origin of a Japanese translation is never answered by the origin of the English text sitting next to it. `resolve()` calls `provenanceFor` for both languages and passes the pair through `metadata.ts`'s `collapseProvenance`, so a dictionary that has never split provenance (every dictionary predating this field) produces the exact same bare-scalar output as before — `provenanceFor`'s own last tier IS `collapseProvenance`'s uniform case, `"community"` on both sides. `group` (the product's own grouping) is NEVER returned by `resolve()`, and is read directly by the assembler as a category fallback. `ui` (`editable`/`readonly`/`absent`) is read the same way — a fact about the PRODUCT'S OWN admin UI, and deliberately not about writability, since almost everything marked `absent` is still settable through the product's API (which is how a provisioning tool sets it); only an extraction that can SEE the UI may set it, which is why it sits with the product facts an overlay is refused. See `assemble.ts` for the one thing it does. `findDictionary()` loads a whole `<product>@<version>.yml` off `metadataDirs` (used by `bind.ts`'s `loadBindSources` and by `assemble.ts`'s materialize, both of which need every key, not just one query's worth) — and, since it is the ONE function all three consumers load a whole dictionary through, it is also the ONE place `findDictionary()` merges in every readable `<product>@<version>.overlay.yml` across ALL `metadataDirs` (T3; more than one overlay is legal — a project-local dir overlays a shared team dictionary without forking it), so none of the three consumers changed. The overlay is the other half of the base/overlay split: the base stays generator-owned (`renderDictionary`, wholesale-rewritten, "GENERATED — do not edit by hand"), the overlay is hand-authored like `sheet.yml` and NEVER written by any generator — regeneration safety comes from the generator physically not knowing overlays exist, not from anyone's discipline about which file they touch. `parseOverlay()` is strict from day one (unlike `parseDictionary`'s lax four-field check — see "Validation status" in the design doc): an overlay entry may set only `description`/`docs_url`/`provenance` (documentation prose; `label`/`default`/`type`/`scope`/`group`/`kind`/`ui`/`options` stay the extraction's to set, or a community claim could reshape materialize's inventory ledger), any other field is an error with a `suggestNearest`-quality "did you mean" hint — duplicated locally (not imported) from `assemble.ts`'s own copy, since `assemble.ts` imports `findDictionary` FROM this module and importing back would be a cycle. The merge (`mergeOverlays`) is fill-only, per language key of `description`: a language the base (or an earlier overlay) already supplies is an error naming the key and language ("the dictionary now supplies ja for db — drop it from the overlay" — the DESC_EXTRA guard from `examples/ansible-keycloak/…/build-dict.ts`, generalized from one generator script into the loader so it runs for every product on every build), and EVERY offending key across every overlay is collected into ONE thrown error (never fail-fast on the first) — a version upgrade that starts supplying several languages at once must not make the author fix-and-rerun to find the next one. An overlay key the base no longer has is the same kind of error, generalizing the same guard's stale-key check. `mergeProv` layers the overlay's per-language provenance patch onto the base entry's own (`provenanceFor`, above) — a base SCALAR is expanded to both keys before patching so filling only `ja` cannot silently widen what `en` claims, a base that is undefined/partial is left exactly that sparse (so `provenanceFor`'s own fallthrough to the document-level default still fires for the language nobody touched — the keycloak `db` case: `en` still resolves through to the doc's `extracted`), and the result collapses back to a bare scalar only when both languages end up defined AND equal. `renderDictionary()` writes the base, so a per-product normalizer builds a typed `DictionaryDoc` instead of re-deriving the file shape; the overlay is never rendered by any function — it is ordinary hand-written YAML. A dictionary is a SHARED asset — the split is "about the product" (values, descriptions, translations → dictionary) vs "about this project" (categories, out_of_scope, `dict_key` aliases → sheet.yml); wording with no product statement behind it goes in the dictionary too but with `provenance: community` on the ENTRY, so the document-level provenance never vouches for it. Custom providers register the same way (CLI `--providers-dir` / auto `./.review-sheet/providers/`) **Naming a file is decided across the sheet, not per row** (`shortestUniqueNames`): a repo-relative path is named by the shortest tail no other path shares, so two roles' `defaults/main.yml` stop merging into one heading holding both their rows; an ABSOLUTE path keeps every segment, because it is where the setting lands on the host — the name a reviewer holds, and the one the paper sheet used — and two distinct absolute paths cannot collide anyway. The fold that removes a component level named after its own file compares DISPLAY names on both sides: the component names the file as the project wrote it and the category as the sheet shows it, and comparing the raw forms meant the fold never fired, so every such row opened a heading holding one heading of the same name.
- `src/bind.ts` — `bindKey(key, dictKey, sources)`: the ONE place a project parameter key is matched against a bound dictionary entry, run ONCE per build (see assemble.ts/enrich.ts below), not re-derived per provider lookup. Tries five tiers in order, stopping at the first with exactly one hit: `alias` (the project's own `dict_key`, verbatim — a human's explicit "these are the same thing"), `exact` (the raw key IS a dictionary key), `prefix` (the binding's `key_prefix` stripped), `leaf` (the last identity-bearing segment of a structural path, via `structural.ts`'s `parseSteps` — handles `attributes["saml.client.signature"]`), `repeat` (a trailing repetition index dropped — `Service.Environment[1]` -> `Service.Environment`; a repeated directive is the same parameter written twice and the product documents it once, and it sits right after `exact` because it IS the key minus bookkeeping no product states, deliberately NOT folded into `leaf`, which would also discard the section and hand it another section's answer), `normalized` (any candidate above with `_`/`-`/`.` stripped and casefolded, tried LAST — this is what lets `httpd_timeout` find `TimeOut` with zero declarations). The organizing principle: normalization that makes two spellings equal erases wiring (delimiter/case, not information) and should need no YAML; normalization that would NOT make them equal, so a human wrote an alias instead, IS information and is preserved. A tier with more than one distinct hit is `BindError` (`isBindError`), never a silent first-source-wins pick. `dict_key: null` (distinct from `undefined`) short-circuits to "no binding" before any tier runs — an explicit severance from an otherwise-coincidental match. `loadBindSources()` is the shared I/O loader (`<product>@<version>.yml` off `metadataDirs`, via `providers/dictionary.ts`'s `findDictionary`) used by both `assemble.ts`'s `bindDrafts` (once per build, all sheets, feeding a `BindingReport`) and `enrich.ts`'s own standalone bind pass (the `import -f` + `--project` path, which never goes through `assembleSheets`). `Binding.docProvenance` is `LangProvenance` (metadata.ts) — a type-only change from this module's own point of view: `bindKey()` carries the bound dictionary DOCUMENT's `provenance` through untouched (scalar or per-language map, whichever the document declared), never interpreting it; only `providers/dictionary.ts`'s `provenanceFor` reads it, layered against the entry's own `provenance`, when the dictionary provider's `resolve()` runs

A strict failure (missing description here; missing category, or an unused project param, in assemble.ts) throws `ScaffoldableBuildError` carrying `ScaffoldEntry[]`; `renderScaffold()` turns that into a paste-able `params:` YAML fragment for `sheet.yml` (placeholders are the literal string `TODO`, never empty — an empty string would fail strict again with no new information), annotated with any dictionary entry the key already binds to; an "unused" entry renders as a comment checklist instead (the fix is deletion/typo-correction, not an addable block). Wired into the CLI's `import` command (`--project`, `--metadata-dir`, `--argument-specs`, `--terraform-variables`, `--lang`, `--native-lang`, `--no-strict-metadata`, `--providers-dir`) as an opt-in step; `verify`/`apply`/`serve` are untouched. `extra.provenance` (a `param.extra` value — plain string, per `input.schema.json`) is written through `formatProvenance()`, which renders a `LangProvenance` (metadata.ts) down to that string: a scalar, or a per-language pair with nothing to disagree with (both sides equal, or only one language ever got a description at all), renders as today's bare token — the case every unmigrated dictionary hits, keeping its output byte-identical; a genuine split renders the fixed-order `en: <p> / ja: <p>`. Deliberately NOT i18n'd (`src/html/i18n.ts`): `extra` values are static strings baked in at generate time, unlike `description`/`remarks` (`LangText`, resolved live by the viewer's `localizeSheets`), so the in-page language toggle cannot re-resolve a joined provenance string the way it re-resolves prose
- `src/assemble.ts` — `assembleSheets`/`assembleSheetsWithReport`: IaC-agnostic layered assembler. Takes `SheetInputs[]` (exactly one base layer + per-instance overlay layers of already-extracted entries, plus embedded literals) → Pattern A (`origin: common`) / Pattern B (`origin: overlay`) params, resolves each row's key (its extracted identity, verbatim, unless `SheetInputs.keyMap` names a product key for it — see `resolveKey`; no sheet-wide "keying" switch, S2 — naming is decided per row, by keyMap membership alone), with a keyMap-mapped row's extracted identity surfaced in an under_key column — `providers/project.ts`'s `underKeyForSheet(projectMeta, sheetName)`, P7: the column's id/label is a display fact declared in sheet.yml, not on `SheetInputs` itself; a sheet with ANY keyMap entry and no under_key declared is a hard error), runs `bindDrafts` per sheet (the single `bind.ts` pass, producing a `SheetBindings` — nested by COMPONENT then key, never by the key alone: two components of one sheet share a key space BY DESIGN (that is the first of the three things a component is), so a dictionary scoped to one of them, or a per-component `dict_key`, makes `port` under one and `port` under the other two different bindings; a flat map gave them one slot and whichever bound last handed the other its description, default and group — silently, and only on the sheets whose whole reason for existing is that the components differ. `EnrichOptions.bindings` is therefore a LOOKUP `(sheet, key, categoryPath) => Binding | undefined` rather than a map: which component a row is in is something only the assembler can say, since the emitted model renders a component as the outermost category and a single-component sheet collapses that level away — so `assembleSheetsWithReport` keeps a per-sheet `{shows, only}` and resolves the component from the category path enrich walks, falling through to the no-component scope for a row that belongs to none. Against ONLY that sheet's own `AssembleOpts.dictionaries[sheetName]` — a `Record<string, SheetDictionaryBinding[]>` keyed by `SheetInputs.name` — never a sibling sheet's, so two sheets bound to different products can't cross-match by accident; produces the per-key `Binding` map AND a `BindingReport` — rows + a per-`BindMethod` tally), files everything under `categoriesForSheet(projectMeta, sheetName)` (providers/project.ts; that sheet's own declared top-level tab order, from sheet.yml — build.yml no longer carries it, P7 — or first-appearance order if it declared none — a project's own `category:` always wins; failing that, a bound row falls back to the dictionary entry's own `group`, flat; failing that, an unbound param has no category and is a hard error). **`category: null`** (distinct from an absent `category:`, exactly as `dict_key: null` is distinct from an absent `dict_key`) is the project declaring the row belongs to NO category — it is about the COMPONENT as a whole and files directly under the component heading, above every category. The admin console a sheet like this mirrors has that place literally: a Keycloak client's Enabled toggle lives in the page header, above the tab strip, and a project's own per-environment input that several of the component's fields are derived from belongs there too. It must be DECLARED and can never be fallen into: `fileDrafts` prepends the component only to a path that already resolved, so `inner === undefined` (no project `category:`, no binding, no materialize fallback) stays the same hard error it is on a component-less sheet. That ordering is the fix for a real hole — prepending the component FIRST made every such row come out length 1, so the empty-path check could not fire and the row landed silently under the component heading; the guard held on a single-component sheet (collapsed, hence length 0) and stopped holding the moment a second component appeared, i.e. a build-breaking omission became a silent one because a sibling was added elsewhere. A declared `category: null` that resolves to nothing (no component level: none at all, or a single one, which is collapsed) is its own error message rather than "no category", since `Sheet.categories` holds every row and a sheet root carries no params — there is nothing for the scaffold to fix by writing a name. **Ghost-tab guard (P7, split P10)**: once a sheet declares a `categories:` list, `fileDrafts` checks every top-level category ACTUALLY USED by a non-materialize draft (a materialized row's parent/group subcategories are exempt outright, since a dictionary's own groups were never something the declared list was meant to enumerate) against it — but what happens on a miss depends on WHERE the category name came from, tracked as two separate maps (`firstProjectCategoryExample`/`firstDictFallbackExample`) instead of one: a name reached because the project itself wrote `category:` in sheet.yml is almost always a typo, and fails the build, naming the offending sheet/key/category plus a `suggestNearest` (Levenshtein, same helper `unusedProjectParams` below uses, and — exported — the one `src/spec.ts` reuses for its own "did you mean" hint on an unknown `build.yml` field) "did you mean" hint; a name reached ONLY through a bound dictionary entry's own `group` fallback (no `category:` written for that key) is a fact about the PRODUCT, not something the project typed — it can never be a typo, so it only warns (`categoryWarnings`, returned by `assembleSheetsWithReport`/`assembleFromSpecWithReport` and printed by the CLI, same non-fatal treatment as `unusedProjectParams`) rather than failing the build; a sheet that declares nothing stays exactly as free as before this guard existed, for both. The MIRROR direction is reported too (a declared category that ordered nothing, with a `suggestNearest` hint drawn from the names actually used) — it was the one place here that stayed silent while `keyglob`/`keytransform` already reported a pattern matching nothing, and it is not harmless: a dictionary's `group` is a PATH, so a name declared in the old flat spelling ("Tokens / Access tokens" for what is now the head "Tokens") orders nothing at all and the tab lands wherever emission order puts it. Checked after the tree is built, since on a component sheet a name can order nothing at the root and still order something inside every component. The project-typed case is what closes a real, observed bug: a param's `category: Generl` (typo of `General`) used to produce a silent third tab with no error and no warning (`verify: 2 ok, 0 warn, 0 error` / `tabs: ['General', 'Generl']`) — the two-file-write shape (assign in sheet.yml, declare order in build.yml) meant the second write was easy to forget; one file removes the failure mode. Before the split, a dictionary `group` an author never typed could ALSO hard-fail the build the same way — meaning a sheet that declared `categories:` had to additionally enumerate every dictionary group any bound param might fall into, exactly the hand-written burden materialize's own exemption already existed to avoid for materialized rows. Then runs `enrich()` (handed `bindDrafts`' bindings so it never re-matches). Binding and materialize travel together on purpose — build.yml used to have a spec-wide `dictionaries:` (in `sheet.yml`) plus a spec-wide `materialize:` restating the same `product`/`version` and tying itself back via a `sheet:` name field, which let the two silently drift apart; now a binding names its own dictionary once, on the one sheet it applies to. A dictionary entry with no documented `default` is EXCLUDED from materialize by default: `origin: "default"` asserts "the product default applies here", which is simply false for a directive the dictionary never recorded a default for — not redundant, factually wrong (measured: 43% of a real materialize run, 122/282 rows, across httpd and Keycloak). `DictionaryMaterialize.includeNoDefault` opts a binding back in when a project has specifically checked the real behavior. `bindingOrFallback` decides the last two tiers of the category fallback: a binding wins whenever its entry HAS a `group`, but a dictionary whose product has no arrangement of its own to state (logrotate's man page lists its directives alphabetically, so the generator sets no `group` rather than inventing one) falls through to the draft's own `fallbackCategoryPath` instead of landing on UNCATEGORIZED — which for an `EmbeddedEntry` is now `categoryPath`, the container the PARSER read the row out of (a rotation policy's log-path block, a `[Section]`). That is strictly last: behind the project's `category:` and behind any binding that actually groups. A bound dictionary's `ui` claim (providers/dictionary.ts) is applied in ONE pass after materialize, so it covers both kinds of `origin: "default"` row — the ones materialize invented and the ones a recipe filed from a snapshot of the product (`static_files`' own `origin: default`) — and it applies to those rows ONLY: `ui: "absent"` means the UI has no field for the parameter, never that it cannot be set, so a row the project DOES write keeps its source map and its review target whatever the UI offers. An unset `absent` row is dropped and an unset `readonly` row is kept but marked `out_of_scope` with `UI_READONLY_REASON` (review-sheet's own bilingual sentence — the fact is the dictionary's, so the wording should be too; a project's own `out_of_scope` is applied later in `fileDrafts` and still wins). `UiReport` carries both key lists per sheet and the CLI prints them: dropping a row is precisely the failure this project refuses to let happen quietly, and the lists are short because a claim only ever reaches rows nobody set. This exclusion depends entirely on the dictionary's own extraction quality — some no-default entries (httpd's `AcceptFilter`/`ErrorDocument`/`Protocol`) DO have a real, undocumented default the dictionary's extraction script simply missed — so it is never silent: `MaterializeReport.noDefault` (count, always in the `import --spec` stderr summary) and `.noDefaultKeys` (the actual keys, opt-in via `--materialize-report <file>`, same shape as `--bind-report`) exist so a project can audit exactly what a dictionary's gaps are hiding, not just how many. `SheetInputs.authoredKeys` (opt-in, `ReadonlySet<string>` of DISPLAY keys — post-keyMap, what a recipe's own set is stated in terms of) is a second, narrower way a row ends up `origin: "default"`, alongside materialize: of the keys a sheet's `layers` (base + overlay) produced, `buildDrafts`' `demotedOrigin` keeps only the ones named there as `overlay`/`common` and demotes every other layer-derived row to `default`, keeping its `instances`/`value`/`source` exactly as resolved — a Terraform plan's `change.after` reports a value the author wrote and one the provider defaulted IDENTICALLY, so `overlay: 178 rows` for a sheet whose source only actually states 85 of them is simply wrong, and the other 93 are the SAME class of row as a materialized one (nobody in this project chose the value), just observed in the plan rather than documented in a dictionary. It is a CHANNEL, not a policy: a recipe that can answer "did my source author this key" (a Terraform plan, checked against the module's own `.tf`) sets it; a recipe that structurally cannot (CDK/Pulumi synth, where authorship lives in program logic no source map recovers) leaves it unset and keeps today's behavior — that is a real limit of the channel, stated here rather than papered over with a guess. Never applied to `embedded[]` (step 3 of `buildDrafts`) — an embedded entry already declares its own `origin` (`embedded` or `default`) explicitly, so there is nothing for this channel to override. Absent (every recipe as of this task) is a no-op: every existing sheet's output is unaffected, byte for byte

- **`StructuralSplit.nest`** (keytransform.ts, applied in `recipes/layered.ts`) — a list nested INSIDE each member of a split, which a Keycloak LDAP store's mappers are. Two things make it more than a second split. The nested members file INSIDE their member's component, under a category named by `nest.under` (`corp-ldap > Mappers > …`) rather than becoming components of their own — a mapper is part of the store, and seventeen components in a row is not what a reviewer is looking at. That category is the LAST-resort one (`EmbeddedEntry.categoryPath`), so a project `category:` and a bound dictionary's own `group` both still outrank it: it says where the row SITS in the file, not what it is about. And **`key_from` names a SIBLING field of the nested member whose VALUE prefixes every one of its keys** — that is what makes the rows bindable at all: a mapper's meaning comes from its TYPE (`providerId`), 16 property names are declared by more than one type at 26.7.1 and 8 of those differ between them in label, help text, default or type, and the type appears NOWHERE in the structural address. Reading a sibling is not a new channel — `by:` already reads one to identify the member; this reads a second field of the same object. It cannot be a string transform, because the value lives in another entry: `nestPrefixes` builds the member->value map in one pass over the file BEFORE any key is derived, and `withNestPrefix` prepends it — together with the member's OWN id, because identity is per COMPONENT and every nested member of one member now shares it, so six mappers' `ldap.attribute` would otherwise be one row six times over — at the two places a key is decided (`buildMapFromSources`, `buildEmbeddedFromStaticFiles`). A member whose `key_from` field is missing is left UNPREFIXED rather than guessed at — the row then fails to bind and the strict gate names it, which is the right failure, since filing it under a neighbour's type would publish one mapper's meaning under another's. The alternative was ~15 hand-written `component:`-scoped dictionary bindings, one per mapper instance, each restating a type the realm file already states — and the two would drift the moment a `providerId` changed, with nothing to notice. Three details fell out of the implementation. The component steps had to stop DROPPING what they do not match (the nested step runs first and the plain step would throw its result away), so non-members are dropped by SHAPE up front instead — after the replaces there is nothing left to test. `split.only` and `nest` are refused together for the same reason: `only` selects members by matching their address, and the nested rows would go with the excluded ones. And a nested component is exempt from the `names:` two-way check: `names:` exists for an id a reader would not recognise and is written once per member, while a nested id is `<member> / <what the deployment called this one>` and there are as many as the deployment has — demanding a name for each would turn a list that grows on its own into one somebody has to keep up with, which is what `nest` exists to remove. The `stale` half still applies. **materialize expands across the axis too** (`SheetInputs.nestedMembers`, read by `materializeDrafts`): an unset option of a `unit` the axis uses lands on every MEMBER, keyed `<member>.<dictionary key>` and filed beside that member's own rows, rather than once under the unit. A single row under the type is a decision nobody can act on — a reviewer setting `is.binary.attribute` sets it on the username mapper or on the email one, never on "user-attribute-ldap-mapper", which is not an object this deployment has. The recipe collects the axis where both facts are in hand (the member's id from its address, its unit from `key_from`); a sheet with no nest passes `undefined` and materialize behaves exactly as before.
- `src/recipes/*.ts` — one `SheetRecipe` per project shape, self-registering at load like `src/parsers/*.ts`. `layered.ts` is the IaC-agnostic core every "one base + per-instance overlay" project shape reduces to: `defaults`/`overlays` (each one path or a list of paths, merged in declaration order — needed when a sheet's base is genuinely assembled from more than one file, e.g. one ECS task definition + one Dockerfile), keyed by each entry's extracted leaf name (`Entry.key`) — a same-file leaf-name collision (a TOML `[[array-of-tables]]`, a JSON array of objects sharing a field name) is a hard `buildMapFromSources` error with a suggested per-source `key`-transform fix, unlike the declared-sources override above (intentional) or `static_files` below (keys by structural path, never collides, and `origin: embedded` unless the entry declares `origin: default` — a file that RECORDS the product's own built-ins rather than shipping them, so its rows get no definition site, verify skips them and apply holds; rejected together with `substitution:`, which merges rows into variables the project does set — see SKILL.md's "`defaults`/`overlays` vs. `static_files`" section) + optional `static_files`, opt-in `include`/`exclude` key globs (`keyglob.ts` — an inventory with one group_vars file per HOST GROUP, the ordinary Ansible layout, holds every role's variables, so without a filter a one-role sheet files the other roles' variables as its own; NOT defaulted to "keys the defaults declare", since an overlay-only variable is a legitimate Pattern B row), and an optional per-source declarative key transform (`keytransform.ts` — a chain of regex/case steps applied AT EXTRACTION TIME, against a source's `Entry.key` or its full `Entry.source.path`, before entries are merged into an `ExtractedMap`; this is what lets a nested or repeated structure — hcl's `variable.<name>.default`, a JSON array element's `environment[name=X].value` — resolve to a flat project key space without a hand-written recipe. `AssembleHooks.keyFor` (assemble.ts) runs too late for this job: by the time a hook sees a parameter, entries whose leaf `Entry.key` collided have already overwritten each other in the map. `data_maps:` (spec level, beside `id_fields`, threaded as `RecipeIO.dataMaps`) declares a path whose CHILDREN are data rather than schema fields, so a dotted data key is spelled `attributes["saml.client.signature"]` instead of reading as three levels; it cannot come from the bound dictionary, or row identity would become a function of which dictionary version is bound, and a free-form map's partial coverage would spell known keys one way and unknown keys the other. A `split: { at, by, only? }` (keytransform.ts's `StructuralSplit`, desugared by `layered.ts` into exactly these steps) is the declarative form of the ONE idiom every identity-keyed list needs — component = the identity segment, key = the remainder, `only:` selecting which members this sheet reviews, and `by:` doubling as the extractor's `id_fields` answer so the same fact is not written twice in two places. It exists because the hand-written form is a project reverse-engineering `structural.ts`'s address grammar (`[field=value]`, quoted only when it must be) in userland regex, which fails by matching nothing; the tool decided the spelling, so the tool writes the pattern. A source's own steps compose AFTER it, which is where the genuine judgement stays. `{ drop: pattern }` (drops when it MATCHES, the mirror of `on_no_match: "drop"`) exists for the selection half, and `steps` is optional so `key: { from: path }` alone no longer has to be spelled as a no-op `^(.*)$ -> $1`. A "drop" step is opt-in per step (default "keep"), and a "drop" pattern that never matched anything is reported back as a warning — silently losing rows is the one failure mode this whole area exists to prevent, see keyglob.ts's `unmatchedPatterns` for the same stance). `defaults` is optional here (omitted → empty base, mirroring `snapshot.ts`'s convention, so a sheet built purely from per-instance overlays still turns every key into a real Pattern B row). No `keyMap` here either — a plain base+overlay layer has no template to derive a product key from, so every row keeps its extracted identity verbatim. `ansible.ts` is now a thin specialization on top of `layered.ts` — it calls `layeredRecipe.load()` for the base/overlay/static_files/include-exclude plumbing and adds only what is genuinely Ansible-specific: Jinja2 `template` rendering, and — whenever a `template` is given, automatically, with no per-sheet flag (S2) — binding a role's `defaults` variables to the PRODUCT's own config keys via `SheetInputs.keyMap`, read off the template's `{{ ansible_var }}` passthroughs — but only for a variable that backs exactly one template entry; one driving two or more directives (httpd's `ProxyPass`/`ProxyPassReverse` sharing a backend variable) has no single product key to claim, so it is filed under ITS OWN NAME instead (no keyMap entry, hence no under_key either — see assemble.ts's `resolveKey`) and reported (`console.warn`, same style as this file's other `skipped (...)` warnings) naming the variable and every entry key it drives, never decided silently; a `defaults` variable the template never resolves into a row at all (never referenced, or only inside a conditional test) is rescued into the base map, appended after every template-derived one in `defaults`'s own order under its own name, ONLY when no overlay sets it either — otherwise it would be entirely invisible (this project never silently drops a row); one some overlay DOES set is left alone, since assemble.ts's own "keys seen only in overlays" sweep already recovers it with its true historical shape (a Pattern B row covering only the instances that set it) — rescuing it here too would fabricate a base value for every instance that never set it. **`templates:` (plural)** covers a sheet whose subject is SEVERAL deployed artifacts — a product's main config file, its systemd unit and its environment file are one subject to a reviewer, and an incumbent sheet being migrated from usually groups them that way. Each entry becomes a COMPONENT (id = the file name with `.j2` stripped, or a declared `component:`), which is what makes the merge possible at all: two systemd units both have `Unit.Description`, and the base map is keyed by the row's own name, so one would silently overwrite the other. Literals therefore go to `embedded[]` (a list, whose entries each carry a `component`) instead of the base map when a sheet is scoped — the same mechanism `static_files` already uses for several files on one sheet; the cost is that embedded rows are appended after the base layer rather than interleaved at their template position, which grouping by component reorders anyway. Variables stay in the SHARED base map keyed by the variable name, because that key is also the overlay lookup key — so per-environment values keep working untouched — and the existing not-1:1 rule is simply counted across the whole sheet: one variable spelling a directive in one file and its equivalent in a second is the same situation as `ProxyPass`/`ProxyPassReverse` sharing a backend, so it earns no product key, and no component either — it belongs to both files, and claiming one would be a guess, so the row sits outside every component heading. `template:` (singular) is unchanged and creates NO component: a sheet that IS one artifact needs no level naming it above every category, and existing sheets keep their row keys and their template-order interleaving byte for byte. Declaring both, or a sheet-wide `deployed_path` alongside `templates:`, is rejected rather than merged — which template the path belonged to would be a guess. `deployed_path` = the task's `dest:` → `Sheet.file_path` shows where the config LANDS and `Sheet.source_file` keeps the template, per the convention types.ts defines. A deployed `file_path` MUST come with `source_file`, else the verify/apply fallback would target a path on the managed host — read, or under `serve --write` written, on the reviewer's own machine. `terraform-plan.ts` is `snapshot` with ONE format's shape written down — a rendered `terraform show -json`: key = `<module>.<type>.<name>[i].<arg>` (the module stays, since `aws_lb.this` is unique only within one; a resource in none gets `root` so every key has one shape), component = the module (`names:` stays the project's), `id_fields: address` because that is how a plan addresses `resource_changes`, and everything that is not a resource argument dropped by failing to match one pattern rather than by a list of section names. It also returns `SheetInputs.dictKeySteps` — how a plan row relates to the PROVIDER's dictionary, which documents `<type>.<arg>` — applied by assemble-spec.ts to any binding that declares no `key_steps` of its own; that follows from the plan's shape, not from anything a project chose, and a project that declares its own still wins. Optional `sources:` (component id -> a directory of `*.tf`, resolved relative to the spec) previews the module's own SOURCE beside the sheet, and deliberately not the plan: the plan IS the extraction subject, but it is a 156 KB machine-generated document whose adjacent lines are punctuation (a `terraform show -json` array index, a closing brace), so previewing it would be worthless even before the size gate in `preview.ts` refuses it outright — what a reviewer needs beside `load_balancer_type = "application"` is the `resource "aws_lb" "this" { }` block it sits in, in the `.tf` a human wrote. The unit is one `ArtifactPreview` per FILE, never per module: concatenating a module's several `.tf` files into one preview would make every line number fiction (the hcl parser's `Entry.source.line` is per-FILE) and `source_file` — the one claim `ArtifactPreview`'s header makes, per file — a lie the moment a module has more than one file, so `main.tf` and `variables.tf` are two previews, `previewId(sheet, component, file)`'s file discriminator keeping them from colliding as bogus instance tabs of each other (see `preview.ts`'s and `app.ts`'s own entries). Each carries `nature: "source"` (types.ts) — `PreviewSource.nature`, threaded through by `previewFile` (and, for symmetry, `previewRendered`, though nothing yet sets it there) — since a `.tf` is authored, never rendered/deployed, and the panel must not claim "Rendered from" over it. The bridge is two pure functions, `tfSourceKey(component, hclPath)` (turns the hcl parser's `resource.<type>.<name>.<rest>` into the `<component>.<type>.<name>.<rest>` shape a plan row uses; `undefined` for every non-`resource.` block — `variable.`/`locals.`/`output.`/`data.`/`terraform.`/`provider.`/`module.` are declarations a plan never reproduces as a `resource_changes` entry, so there is nothing on the plan side for them to line up with) and `normalizeTfKey` (strips `[<digits>]`, the same normalization `DICT_KEY_STEPS` already applies, because the plan JSON renders a nested block as an array — `health_check[0].path` — even where the module's own source never wrote an index). The wiring (`buildRowKeyIndex`/`buildFilePreview`/`buildSourcePreviews`) builds its row-key index from the sheet's OVERLAY layers, not a base — `snapshot.ts` (which this recipe wraps) always emits an EMPTY base layer, so every plan row lives in an overlay — normalizes each layer key and keeps the FIRST raw key per normalized form (a `count`-indexed pair like `node[0].ami`/`node[1].ami` collapses to one normalized form though they are genuinely different rows; the file's one line can only carry one key, so the first wins and a file that actually hits such a group gets ONE aggregated warning naming it, never a silent pick). A hcl entry that resolves to no row (a `variables.tf` declaration, a plan-only provider default with no line in any `.tf`) is skipped with no warning — this is the SAME rule already in force everywhere else in this file: "a row the file has no line for gets none" (see `app.ts`'s `ArtifactPanel` entry) — a `variables.tf` previews with every line keyless, by design, not by omission. Only a component `sources:` names but the sheet produced zero rows for, or a directory that does not exist, is an error (the same two-way discipline the `names:` check above takes); a component whose `.tf` files matched zero rows across the board still warns (not throws), naming the component and suggesting the directory is wrong, since a badly-aimed `sources:` entry is exactly the kind of declared-rule-matched-nothing this project never leaves unnoticed. `sources:` no longer only feeds the preview panel — it also decides row ORIGIN, via `SheetInputs.authoredKeys` (assemble.ts): declaring it is not "I want a sidebar", it is the project stating "this directory IS the module's authored source", which is exactly the authority that channel needs, so there is no opt-out — a component named in `sources:` gets every one of its rows judged, automatically. The judgment reuses the SAME scan that builds the preview (`buildFilePreview`'s `hclAttributeSites` walk): a row matched by some site is `authoredKeys`-named and keeps its overlay/common origin; a row the scan never found an assignment for (a plan-only provider default, same as `idle_timeout` never appearing in any `.tf`) is demoted to `origin: "default"`, keeping its resolved `instances`/`value`/`source` exactly as observed — the same class of row as a materialized one, just observed in the plan rather than documented in a dictionary. This is exactly why `hclAttributeSites` reports every ASSIGNMENT rather than only ones `hclIndex` can VALUE: `skip_final_snapshot = !var.deletion_protection` is an authored decision even though its value is an expression no source map can resolve to a literal, and a discriminator built on `hclIndex` would have wrongly called it provider-resolved. Scoped per COMPONENT, not per sheet: a component with a `sources:` entry gets this treatment, but a component the sheet produced rows for and `sources:` never names is not evidence it authors nothing — absence of a declaration is not evidence of absence of authorship — so it keeps today's behavior, every row staying overlay/common, unjudged. That silence must still be visible: an unjudged component looks identical to a judged one on the rendered sheet unless something says otherwise, so `buildSourcePreviews` warns once per undeclared component (`component "X" has no sources: entry — its origins are unverified`) the same way it already warns about a `sources:` entry matching zero rows. And it is never silent in the other direction either — every JUDGED component prints its own authored/demoted counts (`sources.X: N row(s) authored ..., M demoted to origin: "default"`), so a sheet where half the components are judged and half are not cannot be mistaken for one where every row got the same scrutiny. A row belonging to no component at all (a resource outside every module, dropped by `COMPONENT_STEPS`) can never be named by a `sources:` entry either, so it is folded into "keep today's behavior" the same way, with nothing to warn about since there is no component there to warn on. This lives on `terraform-plan.ts` and not on generic `snapshot.ts`: the address grammar the bridge decodes (`resource.<type>.<name>.<rest>`, module segments, `[<digits>]` array rendering) is Terraform's, not this tool's — a `sources:` on `snapshot` would mean every project re-deriving that grammar in userland regex per project, which is the exact failure mode `terraform-plan.ts`'s own `KEY_STEPS`/`DICT_KEY_STEPS` already exist to avoid one layer up. A conditional line — one inside `{% if %}` — is EVALUATED per instance under this axis rather than dropped: `jinja2.ts`'s `jinjaConditions` returns what governs each line's presence, `truthyJinja` applies Jinja truthiness to the string an extractor gives, and the row exists for the instances that render it (`EmbeddedEntry.instances`, a Pattern B row whose absent instances are simply missing from the list — which is also what finally gives a COMPONENT's rows the instance axis, replacing a warning that displayed the base value for every environment). Only `{% if name %}`/`{% if not name %}` with no `elif`/`else` is understood; a comparison, a filter, a `for`, or an `else` is REPORTED and its lines left out, the same stance `substituteJinja` takes. A test variable the sheet's `include:`/`exclude:` filter hides is reported separately and by name rather than read as Jinja's falsy-undefined — the variables a template needs only in order to RENDER are exactly the ones an author forgets to keep, and silently agreeing drops the line for a reason that has nothing to do with the template. Repetition indices are the TEMPLATE's, so a conditional line before an unconditional sibling of the same directive would renumber the rest for the instances that skip it; that is checked and reported too. The recipe emits **`ArtifactPreview`s** (types.ts) by calling `previewRendered` (`src/preview.ts`) once per template — each rendered WHOLE, per instance, by the same substitution engine every artifact row's value comes from, so the viewer can put the file beside the sheet. What makes it cheap is that a line with no Jinja on it IS the deployed line by identity, so every comment and blank line arrives untouched — which is most of a real config file and exactly what reassembling it from extracted rows cannot produce (measured on a vendor httpd.conf: 356 lines, 35 directives — rows recover a tenth of the file, rendering recovers all of it). The MECHANICS — the line-kind vocabulary (`verbatim`/`substituted`/`absent`/`unrendered`), the `{% if %}` handling, and deduping identical per-instance renderings into one — now live in `previewRendered` itself; see `src/preview.ts`'s own entry below. What stays here are the Ansible-specific DECISIONS handed to it as arguments: the deploy-time variable set is DECLARED as a list (`DEPLOY_TIME_VARS` — Ansible's `ansible_managed` and the `template_*` set) rather than pattern-matched, so a typo'd variable name can never become benign — an `unrendered` line's `cause` (`engine` vs `deploy-time`) is what lets only a genuine gap count toward the panel's warning, since counting `deploy-time` too made it fire on every file in a real project without once pointing at a setting, which buries the case that matters. And `ansible_managed` is resolved, not defaulted, when it carries placeholders: it is read from `ansible.cfg` when the project states it, else from Ansible's own documented default (`ansible-config dump`'s DEFAULT_MANAGED_STR, `Ansible managed`) — a product fact of the kind this project reads out of a registry rather than guesses at, and the FIRST line of every generated file, so leaving it raw put a `{{ }}` at the top of every preview — but a value carrying python-format placeholders (`Ansible managed on {host}`, which Ansible fills per host) cannot be known here, so it is left unresolved rather than printed with its braces showing. `layered.ts` emits previews for `static_files` too, by READING rather than rendering (`previewFile`) — a committed file needs no engine and every line is `verbatim` by identity — but NOT for `defaults`/`overlays`: those are shared (an Ansible group_vars file holds every role's variables, which is why `include:`/`exclude:` exists), so putting one whole into a circulated document would hand on the rows the sheet deliberately filtered out. Both producers now only build a `PreviewSource` and a `LineKeys` map (via `addLineKey`) from what only they know, and hand them with the text to `src/preview.ts` — the size gate lives there too, so every future producer inherits it instead of re-deciding it. `layered.ts` calls `previewFile`, `ansible.ts` calls `previewRendered`; only the decision of WHICH files get a preview (and, for `ansible.ts`, how a variable resolves per instance) stays the recipe's own. Emitted for the VARIABLE axis too, not only `rows: artifact` — `db-url-host` is judged by the `db` lines around it just as much. Never called "the deployed file": recipes run no toolchain, so it is a preview and says so, and the PoC's `check-rendered.sh` diffs it against what real Ansible writes (7 artifacts × 3 environments, exact but for the lines marked `unrendered`). `ansible.ts`'s `rows: artifact` (opt-in per sheet) moves a template-driven sheet's rows onto the ARTIFACT's axis: keyed by the line's structural path, valued at the line's text with each `{{ var }}` substituted (`jinja2.ts`'s `substituteJinja` — a plain `{{ var }}` and the pure filters only; anything else is left as written and REPORTED, because a partial engine that guessed would print a value that looks rendered and is wrong), with the variable moved to `under_key`. It exists because the variable axis structurally cannot hold two things the file contains — the literal text around a variable (`"{{ x }}" proxied` lost its `proxied`) and a variable driving N directives (all four ProxyPass/ProxyPassReverse lines were dropped, with a warning) — both measured by rendering the real templates and diffing. Such a row's source is the variable's site marked `SourceLocation.substituted`, the MIRROR of `ref`: verify checks that the site's value still appears in the row (rather than the row's in the site), and apply HOLDS, because the suggested value is a whole line and deciding which part of it was meant is how a config edit becomes a template edit. `resolveKey` gained a bound->variable direction for it: such a row is already keyed by the product key and still has a variable behind it. Guarded by `tests/artifact-rows.test.ts`, which asserts the recipe's rows against a committed RENDERED fixture rather than a hand-written expectation. `snapshot.ts` (one PRE-RENDERED artifact per instance — `cdk synth`/`terraform plan`/`helm template` — for divergence that lives in program logic: emits an EMPTY base + one overlay per instance so every param is Pattern B, keys by structural path, marks every `source.generated: true` so `apply` HOLDS, and cuts the machine-generated noise down with `include`/`exclude` path globs via the same `keyglob.ts`, `*` within a segment / `**` across). Recipes NEVER execute a toolchain — artifacts are ordinary committed files. Custom recipes register the same way (CLI `--recipes-dir` / auto `./.review-sheet/recipes/`)
- `src/recipes/ansible.ts`'s **`baseline:`** — states the delta from a vendor's shipped file explicitly (a Japanese infra team's most common pattern: take the RPM's config, edit some values, comment out the rest), because `rows: artifact`'s row set is the DEPLOYED file's active lines, so a directive the vendor shipped that this project disabled has no row at all — the decision is visible only as an absence, unable to carry a description, a remark, or a review finding. No comment parsing, deliberately — an earlier sketch proposed extracting `#Directive args` lines from the baseline, and was refused on a MEASUREMENT: RHEL's own `httpd.conf` carries 262 comment lines, and most of the directive-shaped ones are usage EXAMPLES the file's own author left as documentation (`# Listen 12.34.56.78:80`, `# Redirect permanent /foo http://www.example.com/bar`), not disabled settings — there is no reliable way to tell the two apart, and the design does not need to, because **the baseline's ACTIVE directives are the row set**: a vendor directive absent from the deployed file was disabled, whether by commenting or deleting, and the reviewable fact ("we do not have this") is identical either way. The baseline file is a COMMITTED, project-pinned copy, not anything derived (a live fetch from the vendor's repo, a package-manager query at build time): the whole point is reviewability against a FIXED point of comparison — a floating baseline would make the delta answer a different question every time the vendor patches, silently, which is exactly the kind of undetected drift this project's source-map discipline exists to rule out elsewhere, and a committed file gets the same diff/review/pin guarantees as every other input this tool reads. Read with `extractFile` using the SAME parser the deployed artifact resolves to (`formatOf(spec)`, the existing hint that already disambiguates a bare `.conf` for the template) — never comment-scraped, per above. Per key, three shapes: baseline AND deployed both have it → the existing row keeps its `value` and gains `baseline` (the vendor's value, for comparison — `ParameterBase.baseline`, NOT `default`: the two answer different questions and measurably differ, see `types.ts`'s comment); baseline has it, deployed does not → a NEW row, `origin: "baseline"` — a value that is not merely undeclared by this project (`default`'s claim) but not in effect ANYWHERE, which is why `baseline` earns a fifth `Origin` value where the generated-artifact `default` case did not (see `types.ts`'s `Origin` comment and `validate.ts`'s entry); deployed has it, baseline does not → unchanged, this project added it, nothing to record. Scoped to a single `template:` (unscoped) — comparing one vendor file against several distinct deployed files (`templates:`) would need to say which file each vendor key belongs to, which nothing here decides, so it is rejected rather than guessed at. Never silent: the file missing is a named-path error; a zero-key baseline (or zero keys shared with the deployed artifact) is a loud warning naming the file, since a sheet full of "the vendor shipped this and we do not have it" rows would look like a catastrophe rather than the near-certain wrong-file mistake it actually is; the per-template counts (inherited unchanged / changed / added / vendor-only) print unconditionally, the same `console.warn` style the rest of this recipe already uses.
- `src/preview.ts` — the shared engine both artifact-preview producers are built on: `layered.ts`'s `buildEmbeddedFromStaticFiles` calls `previewFile` (T3), and `ansible.ts`'s per-template render+dedupe loop calls `previewRendered` (T4) — both hand in only a `PreviewSource`, the text, and a `LineKeys` map built from what only the caller knows (which line became which row), and neither owns the size gate or the line-kind logic anymore. NOT a fourth plugin registry alongside `parser.ts`/`recipe.ts`/`metadata.ts`: those three each have a genuine dispatch problem — many parsers/recipes/providers exist and the caller does not know in advance which one a file/spec/query needs, so something has to pick one by name or by content. A preview has no such moment: a recipe produces one during its own `load()`, for a file it ALREADY holds and whose nature it already knows (a committed static file, or a template it is about to render) — nothing ever resolves a previewer by name or by content, so a registry here would only be a detour back to the one caller that already had the answer. `MAX_PREVIEW_BYTES` and its refusal live HERE and only here — checked against the source text's own length, in BOTH `previewFile` and `previewRendered`, before any work — so every future producer inherits the gate instead of re-deciding it; refusal always `warn`s (naming the file, its size, the limit, and that the row loses its "show me this line in the file" affordance) and returns `undefined`/`[]`, never windows or truncates, because losing a preview quietly is exactly the failure mode this project exists to prevent. `LineKeys` (`Map<number, string>`) is the one bit of state a caller still owns: the SOURCE file's own 1-based line number — the template `previewRendered` walks, or the committed file `previewFile` reads — mapped to the row's FINAL sheet key, built by the caller (only it knows which line became which row) and attached via `addLineKey` (no-ops on an undefined line, last-write-wins on a collision, matching both existing producers). `PreviewSource.nature`, threaded through by both producers, is passed straight to `ArtifactPreview.nature` when the caller sets it (omitted = today's default "artifact", byte-identical for every producer predating `terraform-plan.ts`'s `.tf`-source bridge, the third caller and the first to pass `"source"`).
