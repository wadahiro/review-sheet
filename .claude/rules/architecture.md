# Architecture

Loaded when working under `src/` or `tests/`. This is the per-module record of
WHY each piece is shaped the way it is — the part that cannot be recovered by
reading the code, only the part that can be re-derived from it was cut.


- `src/html/generate.ts` — packages app JS + CSS + data JSON into a single HTML file
- `src/html/app.ts` — browser-side Preact app (rendering + review UI). Exports `Root`/`App` for `tests/viewer.test.ts` (DOM tests; `init()` is a no-op without the embedded elements, so importing it is safe). Review state is durable or it is not kept: what a pass over a sheet produces is
review items, `out_of_scope` in the hand-authored sheet.yml, and the commit
itself. A session-local "I have looked at this" column was tried and removed — a
per-row read-marker is a value snapshot of the sheet in a worse format than the
committed input.json already is, and "what still needs re-reviewing" is
`diff(reviewed revision, now)` (`review-sheet diff`, or Compare)
- `src/html/i18n.ts` — i18n message definitions (ja/en)
- `src/html/styles.ts` — all CSS as a template string
- `src/prompt.ts` — framework-free model types + source-map resolution + English AI-prompt builder (shared by the browser app and the CLI)
- `src/apply.ts` — deterministic, verified apply core (source map → edits; injected file I/O); held items fall back to the AI prompt
- `src/verify.ts` — source-map verification core (checks each value's source resolves in the real files; injected file I/O). A check that succeeded only because the line+anchor fallback rescued an unresolved structural `path` carries `fallback` and is counted in `VerifyOutcome.fallback` — still `ok` (the value IS there, so no gate should fail), but reported as `OK~` / `line-fallback` and never hidden by `--quiet`, because "resolved by path" and "the path is broken and the line happened to match" are different claims and only the first survives a reordering
- `src/structural.ts` — path-based structural edit/locate for YAML & JSON (surgical, format-preserving; via the `yaml` lib). Paths address maps by key and lists by identity predicate (`services[name=web].port`) or index, so resolution survives reordering. For structured files apply/verify resolve by path FIRST (line+anchor is the fallback); `structuredFormat()` routes yaml/json here and xml to `xml.ts`
- `src/xml.ts` — XML support (via `saxes`): extract element-text/attribute values and surgically edit/locate them by a stable path (`server.connector.@port`, `services.service[name=web].port`). Repeated elements addressed by identity attribute → reorder-robust
- `src/toml.ts` — TOML support (line scan, no extra dependency): `[table]`→nested path, `[[array-of-tables]]`→identity predicate (`service[name=web].replicas`) or index; scalar values only. Same index/locate/edit shape as `xml.ts`
- `src/systemd.ts` — systemd unit support (line scan): `[Section]`+`Key=Value`, repeated keys indexed (`Service.ExecStartPre[1]`, unique param key). Same index/locate/edit shape
- `src/shell.ts` — shell script support (line scan + a quote-aware tokenizer): extracts ONLY the two unambiguous shapes a wrapper script carries reviewable values in — a statement-initial `NAME=value` assignment and a long option with a value (`--region r` / `--region=r`) — keyed by the variable name or by the option WITH its dashes so the two can never collide, repeats indexed. Skips heredoc bodies (payload, not configuration), command substitutions (`$(…)` is a command whose output becomes the value, not a literal), bare flags and short options (`-rf` is indistinguishable from a bundle). `isShell(file, content)` detects it by extension or shebang. Its point is `*.sh.j2`: jinja2 strips `.j2` before resolving the base format, so a templated CLI wrapper's `--secret-id {{ kc_db_secret_name }}` records its templateVar and resolves against the role's variable file
- `src/nginx.ts` — nginx support (char scanner → block tree): directives + `{}` blocks; labeled blocks addressed by label (`http.server.location[/api].proxy_pass`, reorder-robust), repeats indexed. `isNginx(file, content)` detects it (no reliable extension); used by extract/apply/verify
- `src/httpd.ts` — Apache httpd support (line scan → block tree): `Directive args` + `<Tag>…</Tag>` containers by label (`VirtualHost[*:80].DocumentRoot`). `isHttpd(file, content)` detects it — by filename (httpd.conf/apache2.conf/.htaccess), by a `<Tag>` block, or (P10, `looksLikeHttpdDirectives`) by content alone for a bare `*.conf` with no `<Tag>` at all: the RHEL `conf.d/*.conf` layout is one directive-only fragment per module/vhost, so `httpd.conf` + `conf.d/proxy.conf` in the same `import -f` used to extract the first and silently contribute nothing from the second (misdetected as `sysctl`, which found no `=` to extract). The signal is vocabulary shape — Apache directives are `CamelCase value` (no `=`), sysctl/ini are `key = value` — and it requires directive-shaped lines to OUTNUMBER assignment-shaped ones (never a single line) and only ever applies to `.conf`, never an extensionless file, to keep the blast radius small; checked against every file in `examples/` and a real downstream project for an unchanged parser selection before shipping
- `src/haproxy.ts` — HAProxy support (line scan → sections): named sections + directives, repeated directive by first arg (`backend[app].server[web1]`). `isHaproxy(file, content)` detects it. nginx/httpd/haproxy all content-detected because `.conf`/`.cfg` collide with sysctl/ini
- `src/registry.ts` — `sharedRegistry(name)`: the backing array for all three plugin registries (`parser.ts` / `recipe.ts` / `metadata.ts`), keyed off `Symbol.for` so it is process-wide. A plugin's `import { registerParser } from "review-sheet"` resolves from the PLUGIN's location, so when the CLI runs from a different checkout the plugin loads a second copy of `parser.ts`; module identity is by resolved path, so a module-scope array made registration a silent no-op. Only effective when BOTH copies have this — an older `node_modules/review-sheet` still registers into its own array. There is no longer any process-wide mutable *configuration* in this package — only registration goes through `sharedRegistry`; a setting (extraction options, the annotation marker) is threaded as an ordinary argument (`ExtractOptions`, see `parser.ts`) all the way to the call that needs it
- `src/parser.ts` — the `ConfigParser` interface (detect / extract / locate / edit) + `ParserMeta` type + registry (`registerParser`, `resolveParser`, `getParser`, `listParsers`). The core (extract/apply/verify) dispatches through this — NO per-format `if` chains. `ExtractOptions` (`idFields?`, `marker?`) is `extract()`'s optional third argument — configuration threaded as data instead of read from process-wide state; `extract(content, file)`, two arguments, still satisfies the type (TS allows fewer declared params), so a custom parser predating this type is unaffected
- `src/parsers/*.ts` — one `ConfigParser` per format (line, yamljson, xml, toml, systemd, nginx, httpd, haproxy), each wrapping its engine and self-registering at load; `parsers/index.ts` imports them all. Content-detected parsers (nginx/httpd/haproxy) use high priority; `generic` line parser is the lowest-priority fallback. Custom parsers register the same way (CLI `--parsers-dir` / auto `./.review-sheet/parsers/`)
- `src/parser-docs.ts` — pure renderers for per-format documentation pages (from `ParserMeta` on each parser); no fs imports; called from CLI (`parsers` command) and gen-docs script
- `scripts/gen-docs.ts` — writes `skills/review-sheet/formats/<name>.md` per parser + injects index/table into SKILL.md and README.md between `<!-- parsers:start -->`/`<!-- parsers:end -->` markers; run with `bun run docs`. Format docs are generated from each parser's `meta` field (see `skills/review-sheet/formats/`)
- `src/extract.ts` — `extractFile(content, file, format?, opts?: ExtractOptions)` = `getParser(format) ?? resolveParser(file, content)` → `parser.extract(content, file, opts)`; plus `buildInput(files, opts?)` and the YAML/JSON engine `extractTree(content, opts?)`. `buildInputWithReport(files, opts?)` is the same build, plus a `BuildReport` (`{ files: { file, parser?, count }[] }`) naming which parser EVERY file resolved to and how many entries it produced — `buildInput` is now a thin wrapper that discards the report (same relationship as `assembleSheets`/`assembleSheetsWithReport`). This exists because `buildInput`'s per-file `continue` on zero entries used to be silent the moment at least one OTHER file in the same call produced something: mixing a working `httpd.conf` with a misdetected `proxy.conf` reported "Extracted 12 parameter(s) from 2 file(s)" with no sign the second file contributed nothing (P10 bug 1) — the CLI's `import -f` now reads the report and warns, by file AND by resolved parser name, for every zero-count file (not an error: a file that is legitimately all comments is not a mistake, but which parser was tried must never be silent, so a genuine misdetection is fixable with `--format`). Source-map extraction is exported from `index.ts` for conversion scripts. `opts.idFields` extends the list of field names that identify a list-of-maps item (built-ins: name/id/key), tried FIRST so an explicit statement about the project's data beats the generic guess — without it Keycloak's `clientId`-keyed clients fall back to a positional `clients[0]`. Threaded as data, spec → `assembleFromSpecWithReport` builds `RecipeIO.extractOptions` (from `build.yml`'s `id_fields`) → a recipe passes it to every `extractFile()` call it makes → `getRecipe`/`resolveParser` need no global; the CLI's `import -f` path passes the same `ExtractOptions` explicitly built from `--id-fields`/`--annotation-marker`. `ExtractOptions.marker` (parser.ts) travels the same way all the way to `locate`/`edit`, not just `extract` — `ConfigParser.locate`/`.edit` both take the same optional `opts` last, so `verifySources`/apply's core pass it straight through and the ts/py annotation parsers' `annotationLocate`/`annotationEdit` read `opts?.marker` instead of any process-wide state; a parser predating `ExtractOptions` (fewer declared params) is unaffected, since TS allows an implementation with fewer parameters than its declared type
- `src/diff.ts` — pure diff between two snapshots → status model (per sheet/category/param, and per-instance value cells for Pattern B); used for summaries/tests. `alignValues()` owns the value-cell pairing and is shared with `diffview.ts` so the CLI and the Compare overlay can never disagree: a row that is Pattern A on one side and Pattern B on the other is compared by expanding the shared value across the other side's instances (that is exactly what `origin: common` asserts), so an equivalent row reads `unchanged` instead of every cell coming out added/removed — which is what makes diffing two DIFFERENT sheets (old platform vs new, during a staged migration) an equivalence check rather than noise
- `src/diffview.ts` — pure builder for the Compare *overlay*: merges two versions into render-ready sheets (union, removed kept in place) + synthetic reviews (changed values as old→new) + a status map. The viewer renders this through the normal ParamTable, so Compare keeps the real sheet look (tabs/freeze/outline/search), not a separate diff layout
- `src/types.ts` — public type definitions (input model incl. `SourceLocation`, review schema, options)
- `src/validate.ts` — ajv schema validation
- `src/cli.ts` — CLI entry point (import / generate / validate / verify / apply / serve). `diff -i base.json -i current.json` prints what changed between two snapshots (the reviewed revision's input.json vs now — the "what still needs review" question, answered from VCS rather than from a per-row ledger). `serve` runs a `Bun.serve` on 127.0.0.1 exposing `POST /api/apply` (computeApply → optional write) and `/api/verify`; the embedded app (generated with `server:true`) calls them so reviewers apply edits straight to local files. The apply/verify cores are reused unchanged (pure, injected I/O)
- `src/metadata.ts` — the `MetadataProvider` interface (`resolve(query, ctx)`) + `ParameterSheetInput`-independent registry (`registerMetadataProvider`, `resolveMetadata`, `getMetadataProvider`, `listMetadataProviders`), mirroring `parser.ts` (array registry, replace-by-name, priority sort at resolve). `MetadataQuery.binding` carries the ALREADY-RESOLVED `bind.ts` `Binding` for this key (or `undefined` — most keys have none), run once per build before any provider sees the query; no provider re-derives it. `MetadataQuery.variable` carries a row's ORIGINAL extracted identity when `assemble.ts`'s `keyMap` renamed it to a product key (e.g. Ansible's `kc_hostname` filed as `hostname`) — a fallback for a native channel keyed by the variable name, not the row's current display key (`argument-specs.ts` is the one provider that reads it; see its own entry below). Built from `assemble.ts`'s per-`Draft` `variable` and handed to `enrich()` as `EnrichOptions.variables` (sheet → row key → variable), independent of whether the project declared an `under_key` display column for it. `description`/`remarks` are `LangText` (`string | { en, ja }`, defined + `pickLang`ed in `types.ts`): providers carry the full map through **unresolved** (no per-lang collapse), so the browser viewer can switch languages at display time. `resolveMetadata` merges providers in priority order (project 100 → argument-specs/terraform-variables 50 → dictionary 30), but the two `LangText` fields (`description`/`remarks`) merge PER LANGUAGE KEY, not field-wise first-wins like every other field: this is what lets `en` come from the value's own native channel (Terraform's `description = "..."`, Ansible's argument_specs `description:`) while `ja` comes from `sheet.yml`, without either duplicating the other. A plain `string` result (what a native channel returns) claims and locks the WHOLE field the moment it lands on an empty slot — there is no "other language" to merge into a language-agnostic string — while a `{ en?, ja? }` object only fills the keys still open; `MetadataContext.nativeLang` (`"en" | "ja"`, default `"en"`, `build.yml`'s `enrich.native_lang` / CLI `--native-lang`) is what tells a native-channel provider which language its own plain string IS, via `nativeLangText()`, so it can hand `resolveMetadata` a properly-tagged `{ [nativeLang]: text }` instead of a bare string that would wrongly lock the field for every language at once. `Provenance` is widened to `LangProvenance = Provenance | { en?; ja? }` — the same per-language shape `LangText` already has, because a description's two languages can genuinely trace to two different sources. `resolveMetadata` now credits provenance PER LANGUAGE KEY: `mergeLangField` reports back WHICH language keys it actually filled (not just whether it contributed), and `provByLang[lang]` is set from whichever provider's result filled that slot — replacing the old "the provider that filled the field's FIRST language key wins the whole field" approximation, which was simply wrong the instant two providers split a description (verified: it was already wrong for a SHIPPED example, `examples/ansible-httpd`'s `ServerTokens`/`MaxRequestWorkers` — `argument-specs.ts` supplies `en`, the `httpd@2.4` dictionary supplies `ja` via the still-open-slot fill `mergeLangField` documents — even though the migration design this task implements predicted no shipped example would move). `collapseProvenance` (also used by `providers/dictionary.ts`, see its own entry) reduces a uniform, or single-language, per-language pair back to the bare scalar before it reaches `ResolvedMetadata.provenance`, which is what keeps every provider/dictionary that has never actually split a description byte-identical to its pre-`LangProvenance` output. `provenanceForLang` is this module's own SINGLE-layer lookup (one provider's own result, scalar-or-map, no document-level fallback) — distinct from `providers/dictionary.ts`'s `provenanceFor`, a separate 4-tier resolution (entry map → entry scalar → doc map → doc scalar → `"community"`) that only the dictionary provider needs; both are deliberately NOT `pickLang` — `pickLang`'s cross-language fallback is right for prose (show something) and wrong for a trust claim (a Japanese translation's origin is never answered by the English text's origin next to it)
- `src/providers/*.ts` — one `MetadataProvider` per source (project, argument-specs, terraform-variables, dictionary), self-registering at load like `src/parsers/*.ts`; `providers/index.ts` imports them all, then snapshots the just-registered names as `BUILT_IN_PROVIDER_NAMES` — the one place "what counts as a built-in" is derived instead of hand-copied (six test files used to keep their own hard-coded allowlist for stubbing out non-built-in providers between tests; adding a provider and forgetting one copy made it silently no-op depending on test run order — see `tests/only-builtin-providers.ts` for the single surviving copy). `project.ts` reads the project's own metadata file (`sheet.yml`, wins every field it sets, provenance `project`; also the sole source of a param's `category` and `dict_key`, both read directly rather than through `resolve()` — see `bind.ts`). `ProjectMetaDoc` is `{ params?, categories?, under_key? } | { sheets? }` — flat `params:`/`categories:`/`under_key:` (a single spec-wide table plus that one sheet's display config) for a single-sheet spec / `import -f --project`, or `sheets: { <sheet name>: { params:, categories:, under_key: } }` for a multi-sheet one; `loadProjectMeta` rejects a file setting both top-level and `sheets:` (no flat fallback under `sheets:` — see below for why), and `paramsForSheet`/`categoriesForSheet`/`underKeyForSheet`(doc, sheet) are the one place either shape is read: a `sheets:` doc returns ONLY that sheet's own value (an unnamed/unknown sheet gets `{}`/`[]`/`undefined`, never another sheet's), a flat doc returns the same value regardless of `sheet`. This is what closes a real leakage bug: with flat `params:`, two sheets sharing an extraction source (e.g. two Ansible roles reading the same group_vars file) share a key's category/description too, so a key that leaks from one sheet's drafts into another's (a missing `exclude:` filter, a renamed variable) can borrow the WRONG sheet's documentation and file in looking legitimate, no error — `sheets:` makes that key resolve against a namespace that never declared it, so the ordinary "no category"/"no description" strict gates name it instead. `categories`/`under_key` (P7) — a sheet's top-level tab display order and the ansible recipe's under_key column label — moved here from build.yml: both are display facts about how a sheet is READ, the same kind of fact `category:`/`out_of_scope:` already are, not about where its data comes from; splitting the assignment (sheet.yml) from the tab order (build.yml) let a second, easy-to-forget write silently produce a "ghost tab" (a category nobody declared showing up with no error, no warning — verified: `verify: 2 ok, 0 warn, 0 error` / `tabs: ['General', 'Generl']` for a single typo'd `category: Generl`). `checkProjectMetaSheets(doc, knownSheets)` fails the build if `sheets:` names a sheet the build has no `SheetInputs` for (same discipline as `assemble.ts`'s `dictionaries` sheet-name check). `argument-specs.ts` reads Ansible `meta/argument_specs.yml` and `terraform-variables.ts` reads Terraform `variable "x" { description = ... }` blocks (via `extractFile()` — no bespoke HCL parsing), both provenance `community`, same priority (the ecosystem's own metadata channel for the value next door, authored by whoever wrote the role/module); NEITHER is sheet-scoped the way `project.ts` now is — a spec-wide list, read the same regardless of which sheet is asking — a narrower, currently-unaddressed instance of the same class of leakage. `argument-specs.ts` matches `query.key` first, falling back to `query.variable` (see `metadata.ts`) when the two differ and the first miss — so a role's own variable-keyed entry (`kc_hostname`) stays reachable for a row `keyMap` renamed to the product's key (`hostname`) instead of going permanently dead the moment the rename happens; `terraform-variables.ts` has no such fallback (Terraform variables are never renamed by a recipe the way `keyMap` renames an Ansible variable, so there is nothing for it to fall back from). Both wrap their plain-string `description` as `{ [nativeLang]: text }` (`nativeLangText()`, `MetadataContext.nativeLang`) rather than returning a bare string, since a native channel's text is written in ONE language and a bare string would tell `resolveMetadata`'s per-language merge "this speaks for every language at once" (see `metadata.ts`); `dictionary.ts` is a plain lookup off `query.binding` — no key matching or file access of its own (see `bind.ts`) — returning `entry.description`/`default`/`type`/`scope`/`docs_url`/provenance for the already-resolved `DictionaryParam`; `DictionaryDoc.provenance`/`DictionaryParam.provenance` are `LangProvenance` (metadata.ts) — a document can carry `{ en: official, ja: community }` once (nginx/httpd: hand-transcribed English, this repo's own Japanese translation) instead of forcing a per-entry override onto every one of its parameters, and an entry can override just one language over that default (Keycloak's `db`: no entry override for `en`, so it falls through to the document's `extracted`; `ja` is entry-level `community` — a hand-written translation the product never shipped, which the OLD single-scalar `provenance` field could not help but credit as `extracted` too). `provenanceFor(lang, entryProv, docProv)` resolves ONE language through four tiers, each checked in full before falling to the next — entry map's key -> entry scalar -> doc map's key -> doc scalar -> `"community"` — and deliberately does NOT fall back to the SAME map's other language key the way `pickLang` (types.ts) would: `pickLang`'s cross-language fallback exists to put SOME prose on screen, which is right for `description`/`remarks`, but wrong for a trust claim — the origin of a Japanese translation is never answered by the origin of the English text sitting next to it. `resolve()` calls `provenanceFor` for both languages and passes the pair through `metadata.ts`'s `collapseProvenance`, so a dictionary that has never split provenance (every dictionary predating this field) produces the exact same bare-scalar output as before — `provenanceFor`'s own last tier IS `collapseProvenance`'s uniform case, `"community"` on both sides. `group` (the product's own grouping) is NEVER returned by `resolve()`, and is read directly by the assembler as a category fallback. `findDictionary()` loads a whole `<product>@<version>.yml` off `metadataDirs` (used by `bind.ts`'s `loadBindSources` and by `assemble.ts`'s materialize, both of which need every key, not just one query's worth) — and, since it is the ONE function all three consumers load a whole dictionary through, it is also the ONE place `findDictionary()` merges in every readable `<product>@<version>.overlay.yml` across ALL `metadataDirs` (T3; more than one overlay is legal — a project-local dir overlays a shared team dictionary without forking it), so none of the three consumers changed. The overlay is the other half of the base/overlay split: the base stays generator-owned (`renderDictionary`, wholesale-rewritten, "GENERATED — do not edit by hand"), the overlay is hand-authored like `sheet.yml` and NEVER written by any generator — regeneration safety comes from the generator physically not knowing overlays exist, not from anyone's discipline about which file they touch. `parseOverlay()` is strict from day one (unlike `parseDictionary`'s lax four-field check — see "Validation status" in the design doc): an overlay entry may set only `description`/`docs_url`/`provenance` (documentation prose; `default`/`type`/`scope`/`group`/`kind`/`since`/`until` stay the extraction's to set, or a community claim could reshape materialize's inventory ledger), any other field is an error with a `suggestNearest`-quality "did you mean" hint — duplicated locally (not imported) from `assemble.ts`'s own copy, since `assemble.ts` imports `findDictionary` FROM this module and importing back would be a cycle. The merge (`mergeOverlays`) is fill-only, per language key of `description`: a language the base (or an earlier overlay) already supplies is an error naming the key and language ("the dictionary now supplies ja for db — drop it from the overlay" — the DESC_EXTRA guard from `examples/ansible-keycloak/…/build-dict.ts`, generalized from one generator script into the loader so it runs for every product on every build), and EVERY offending key across every overlay is collected into ONE thrown error (never fail-fast on the first) — a version upgrade that starts supplying several languages at once must not make the author fix-and-rerun to find the next one. An overlay key the base no longer has is the same kind of error, generalizing the same guard's stale-key check. `mergeProv` layers the overlay's per-language provenance patch onto the base entry's own (`provenanceFor`, above) — a base SCALAR is expanded to both keys before patching so filling only `ja` cannot silently widen what `en` claims, a base that is undefined/partial is left exactly that sparse (so `provenanceFor`'s own fallthrough to the document-level default still fires for the language nobody touched — the keycloak `db` case: `en` still resolves through to the doc's `extracted`), and the result collapses back to a bare scalar only when both languages end up defined AND equal. `renderDictionary()` writes the base, so a per-product normalizer builds a typed `DictionaryDoc` instead of re-deriving the file shape; the overlay is never rendered by any function — it is ordinary hand-written YAML. A dictionary is a SHARED asset — the split is "about the product" (values, descriptions, translations → dictionary) vs "about this project" (categories, out_of_scope, `dict_key` aliases → sheet.yml); wording with no product statement behind it goes in the dictionary too but with `provenance: community` on the ENTRY, so the document-level provenance never vouches for it. Custom providers register the same way (CLI `--providers-dir` / auto `./.review-sheet/providers/`)
- `src/bind.ts` — `bindKey(key, dictKey, sources)`: the ONE place a project parameter key is matched against a bound dictionary entry, run ONCE per build (see assemble.ts/enrich.ts below), not re-derived per provider lookup. Tries five tiers in order, stopping at the first with exactly one hit: `alias` (the project's own `dict_key`, verbatim — a human's explicit "these are the same thing"), `exact` (the raw key IS a dictionary key), `prefix` (the binding's `key_prefix` stripped), `leaf` (the last identity-bearing segment of a structural path, via `structural.ts`'s `parseSteps` — handles `attributes["saml.client.signature"]`), `normalized` (any candidate above with `_`/`-`/`.` stripped and casefolded, tried LAST — this is what lets `httpd_timeout` find `TimeOut` with zero declarations). The organizing principle: normalization that makes two spellings equal erases wiring (delimiter/case, not information) and should need no YAML; normalization that would NOT make them equal, so a human wrote an alias instead, IS information and is preserved. A tier with more than one distinct hit is `BindError` (`isBindError`), never a silent first-source-wins pick. `dict_key: null` (distinct from `undefined`) short-circuits to "no binding" before any tier runs — an explicit severance from an otherwise-coincidental match. `loadBindSources()` is the shared I/O loader (`<product>@<version>.yml` off `metadataDirs`, via `providers/dictionary.ts`'s `findDictionary`) used by both `assemble.ts`'s `bindDrafts` (once per build, all sheets, feeding a `BindingReport`) and `enrich.ts`'s own standalone bind pass (the `import -f` + `--project` path, which never goes through `assembleSheets`). `Binding.docProvenance` is `LangProvenance` (metadata.ts) — a type-only change from this module's own point of view: `bindKey()` carries the bound dictionary DOCUMENT's `provenance` through untouched (scalar or per-language map, whichever the document declared), never interpreting it; only `providers/dictionary.ts`'s `provenanceFor` reads it, layered against the entry's own `provenance`, when the dictionary provider's `resolve()` runs
- `src/enrich.ts` — `enrich(input, opts)`: a library pass run AFTER assembly (not part of extract/buildInput) that fills `description`/`default`/`remarks`/`docs_url`/`type`/`scope` from the metadata provider registry, fill-only (never overwrites a value the project already set); `description`/`remarks` are stored as `LangText` maps (not collapsed to one language — the viewer's `localizeSheets` resolves them per the active `lang`, so the in-page language toggle switches the prose live) and never touching `value`/`source`/`additional_sources`/`instances`. Strict by default: an in-scope parameter with no `description` after enrichment fails the build, naming each offender (`sheet > category > key`) — this includes `origin: embedded` params (literals baked into the deployable source), which are in review scope like any other param; only params/categories carrying `out_of_scope` (a `{ reason, owner? }` object marking a review-remit exclusion, not a statement about mechanism) are skipped entirely, exempt from strict. `EnrichOptions.bindings` (a sheet→key→`Binding` map) is what `assembleSheets` hands in — its own single bind pass already ran; when omitted (the `import -f` + `--project` path, which has no `keyMap` concept at all), `enrich()` runs that same pass itself via `bind.ts`'s `bindKey`/`loadBindSources` directly against the input model's own keys. `EnrichOptions.variables` (a sheet→key→variable map, mirroring `bindings`) is `assembleSheets`'s per-`Draft` `variable` for every `keyMap`-renamed row, handed through as `MetadataQuery.variable`; omitted the same way on that same standalone path. A strict failure (missing description here; missing category, or an unused project param, in assemble.ts) throws `ScaffoldableBuildError` carrying `ScaffoldEntry[]`; `renderScaffold()` turns that into a paste-able `params:` YAML fragment for `sheet.yml` (placeholders are the literal string `TODO`, never empty — an empty string would fail strict again with no new information), annotated with any dictionary entry the key already binds to; an "unused" entry renders as a comment checklist instead (the fix is deletion/typo-correction, not an addable block). Wired into the CLI's `import` command (`--project`, `--metadata-dir`, `--argument-specs`, `--terraform-variables`, `--lang`, `--native-lang`, `--no-strict-metadata`, `--providers-dir`) as an opt-in step; `verify`/`apply`/`serve` are untouched. `extra.provenance` (a `param.extra` value — plain string, per `input.schema.json`) is written through `formatProvenance()`, which renders a `LangProvenance` (metadata.ts) down to that string: a scalar, or a per-language pair with nothing to disagree with (both sides equal, or only one language ever got a description at all), renders as today's bare token — the case every unmigrated dictionary hits, keeping its output byte-identical; a genuine split renders the fixed-order `en: <p> / ja: <p>`. Deliberately NOT i18n'd (`src/html/i18n.ts`): `extra` values are static strings baked in at generate time, unlike `description`/`remarks` (`LangText`, resolved live by the viewer's `localizeSheets`), so the in-page language toggle cannot re-resolve a joined provenance string the way it re-resolves prose
- `src/assemble.ts` — `assembleSheets`/`assembleSheetsWithReport`: IaC-agnostic layered assembler. Takes `SheetInputs[]` (exactly one base layer + per-instance overlay layers of already-extracted entries, plus embedded literals) → Pattern A (`origin: common`) / Pattern B (`origin: overlay`) params, resolves each row's key (its extracted identity, verbatim, unless `SheetInputs.keyMap` names a product key for it — see `resolveKey`; no sheet-wide "keying" switch, S2 — naming is decided per row, by keyMap membership alone), with a keyMap-mapped row's extracted identity surfaced in an under_key column — `providers/project.ts`'s `underKeyForSheet(projectMeta, sheetName)`, P7: the column's id/label is a display fact declared in sheet.yml, not on `SheetInputs` itself; a sheet with ANY keyMap entry and no under_key declared is a hard error), runs `bindDrafts` per sheet (the single `bind.ts` pass, producing a `SheetBindings` — nested by COMPONENT then key, never by the key alone: two components of one sheet share a key space BY DESIGN (that is the first of the three things a component is), so a dictionary scoped to one of them, or a per-component `dict_key`, makes `port` under one and `port` under the other two different bindings; a flat map gave them one slot and whichever bound last handed the other its description, default and group — silently, and only on the sheets whose whole reason for existing is that the components differ. `EnrichOptions.bindings` is therefore a LOOKUP `(sheet, key, categoryPath) => Binding | undefined` rather than a map: which component a row is in is something only the assembler can say, since the emitted model renders a component as the outermost category and a single-component sheet collapses that level away — so `assembleSheetsWithReport` keeps a per-sheet `{shows, only}` and resolves the component from the category path enrich walks, falling through to the no-component scope for a row that belongs to none. Against ONLY that sheet's own `AssembleOpts.dictionaries[sheetName]` — a `Record<string, SheetDictionaryBinding[]>` keyed by `SheetInputs.name` — never a sibling sheet's, so two sheets bound to different products can't cross-match by accident; produces the per-key `Binding` map AND a `BindingReport` — rows + a per-`BindMethod` tally), files everything under `categoriesForSheet(projectMeta, sheetName)` (providers/project.ts; that sheet's own declared top-level tab order, from sheet.yml — build.yml no longer carries it, P7 — or first-appearance order if it declared none — a project's own `category:` always wins; failing that, a bound row falls back to the dictionary entry's own `group`, flat; failing that, an unbound param has no category and is a hard error). **`category: null`** (distinct from an absent `category:`, exactly as `dict_key: null` is distinct from an absent `dict_key`) is the project declaring the row belongs to NO category — it is about the COMPONENT as a whole and files directly under the component heading, above every category. The admin console a sheet like this mirrors has that place literally: a Keycloak client's Enabled toggle lives in the page header, above the tab strip, and a project's own per-environment input that several of the component's fields are derived from belongs there too. It must be DECLARED and can never be fallen into: `fileDrafts` prepends the component only to a path that already resolved, so `inner === undefined` (no project `category:`, no binding, no materialize fallback) stays the same hard error it is on a component-less sheet. That ordering is the fix for a real hole — prepending the component FIRST made every such row come out length 1, so the empty-path check could not fire and the row landed silently under the component heading; the guard held on a single-component sheet (collapsed, hence length 0) and stopped holding the moment a second component appeared, i.e. a build-breaking omission became a silent one because a sibling was added elsewhere. A declared `category: null` that resolves to nothing (no component level: none at all, or a single one, which is collapsed) is its own error message rather than "no category", since `Sheet.categories` holds every row and a sheet root carries no params — there is nothing for the scaffold to fix by writing a name. **Ghost-tab guard (P7, split P10)**: once a sheet declares a `categories:` list, `fileDrafts` checks every top-level category ACTUALLY USED by a non-materialize draft (a materialized row's parent/group subcategories are exempt outright, since a dictionary's own groups were never something the declared list was meant to enumerate) against it — but what happens on a miss depends on WHERE the category name came from, tracked as two separate maps (`firstProjectCategoryExample`/`firstDictFallbackExample`) instead of one: a name reached because the project itself wrote `category:` in sheet.yml is almost always a typo, and fails the build, naming the offending sheet/key/category plus a `suggestNearest` (Levenshtein, same helper `unusedProjectParams` below uses, and — exported — the one `src/spec.ts` reuses for its own "did you mean" hint on an unknown `build.yml` field) "did you mean" hint; a name reached ONLY through a bound dictionary entry's own `group` fallback (no `category:` written for that key) is a fact about the PRODUCT, not something the project typed — it can never be a typo, so it only warns (`categoryWarnings`, returned by `assembleSheetsWithReport`/`assembleFromSpecWithReport` and printed by the CLI, same non-fatal treatment as `unusedProjectParams`) rather than failing the build; a sheet that declares nothing stays exactly as free as before this guard existed, for both. The project-typed case is what closes a real, observed bug: a param's `category: Generl` (typo of `General`) used to produce a silent third tab with no error and no warning (`verify: 2 ok, 0 warn, 0 error` / `tabs: ['General', 'Generl']`) — the two-file-write shape (assign in sheet.yml, declare order in build.yml) meant the second write was easy to forget; one file removes the failure mode. Before the split, a dictionary `group` an author never typed could ALSO hard-fail the build the same way — meaning a sheet that declared `categories:` had to additionally enumerate every dictionary group any bound param might fall into, exactly the hand-written burden materialize's own exemption already existed to avoid for materialized rows. Then runs `enrich()` (handed `bindDrafts`' bindings so it never re-matches). Sync (all injected I/O in this repo is). `bindDrafts`/`fileDrafts` read the project metadata through `paramsForSheet(projectMeta, sheetName)` (providers/project.ts) — never a bare `projectMeta.params[key]` — so a `sheets:`-namespaced doc resolves each sheet's OWN table only; `checkProjectMetaSheets` validates `sheets:` against the build's real sheet names right after loading it. `assembleSheetsWithReport` also returns `unusedProjectParams` — keys the project metadata describes that NO sheet produced, the mirror image of the strict-metadata gate (that one catches a param with no description; this catches a description with no param); under a `sheets:` doc this is scoped per sheet too (a key declared for sheet A stays unused for A even if sheet B's drafts happen to produce a same-named key — a build-wide check would wrongly call it used) and each entry prints as `"<sheet> > <key>"` — and `binding: BindingReport`, surfaced by `import --spec` as a stderr tally plus every `normalized`-tier row unconditionally on stdout (inference is the one tier where a guess, not a literal or declared alias, decided the binding) and, opt-in, a full `--bind-report <file>` JSON dump. `AssembleHooks` (`keyFor` → `mapParam` → `finalize`) is the Level-2 escape hatch: they run BEFORE enrich, so a hook can fix a strict-metadata failure but never hide one. `materialize` (`DictionaryMaterialize`, carried directly on a `SheetDictionaryBinding` — `SheetDictionaryBinding = DictionaryBinding & { materialize? }` — not a separate declaration) expands that ONE bound dictionary's remaining keys into `origin: "default"` rows so the sheet becomes the **exhaustive ledger** the Japanese パラメータシート tradition expects (write everything down, mark what is out of scope) — keyed by the dictionary key itself, nested two levels under a "product defaults" parent + the dictionary's own `group` (a project's hand-declared categories, and an ordinary bound row's flat `group` fallback above, are unaffected), and only the FALLBACK category is relaxed: a project-set param with no category is still a hard error. Binding and materialize travel together on purpose — build.yml used to have a spec-wide `dictionaries:` (in `sheet.yml`) plus a spec-wide `materialize:` restating the same `product`/`version` and tying itself back via a `sheet:` name field, which let the two silently drift apart; now a binding names its own dictionary once, on the one sheet it applies to. A dictionary entry with no documented `default` is EXCLUDED from materialize by default: `origin: "default"` asserts "the product default applies here", which is simply false for a directive the dictionary never recorded a default for — not redundant, factually wrong (measured: 43% of a real materialize run, 122/282 rows, across httpd and Keycloak). `DictionaryMaterialize.includeNoDefault` opts a binding back in when a project has specifically checked the real behavior. This exclusion depends entirely on the dictionary's own extraction quality — some no-default entries (httpd's `AcceptFilter`/`ErrorDocument`/`Protocol`) DO have a real, undocumented default the dictionary's extraction script simply missed — so it is never silent: `MaterializeReport.noDefault` (count, always in the `import --spec` stderr summary) and `.noDefaultKeys` (the actual keys, opt-in via `--materialize-report <file>`, same shape as `--bind-report`) exist so a project can audit exactly what a dictionary's gaps are hiding, not just how many
- `src/assemble-spec.ts` — `assembleFromSpec` / `assembleFromSpecWithReport` / `buildFromSpecFile`: the `build.yml` → `ParameterSheetInput` composition (run each sheet's recipe → assembleSheets), exported so a project can keep its spec and pass `hooks` instead of dropping to a hand-written converter. `import --spec` calls exactly this — one implementation, no drift. Builds one `ExtractOptions` (`{ idFields: spec.id_fields, marker: opts.marker }`) and hands it to every recipe via `RecipeIO.extractOptions` — configuration passed as data all the way down, no process-wide setting anywhere in the path
- `src/recipe.ts` — the `SheetRecipe` interface (`name`/`schema`/`load(sheetSpec, io)`) + registry (`registerRecipe`, `getRecipe`, `listRecipes`), mirroring `parser.ts` but resolved by name (a spec always names its recipe — no content detection). `RecipeIO.extractOptions?: ExtractOptions` carries the spec/CLI's extraction configuration to every `extractFile()` call a recipe makes (see assemble-spec.ts); `undefined` for a recipe that predates the field simply means the callee's own built-in defaults apply (`DEFAULT_ID_FIELDS`, `DEFAULT_MARKER`) — there is no process-wide setting left to fall back to. `src/spec.ts` — `loadBuildSpec`: the declarative `build.yml`, ajv-validated at both levels (spec schema + each recipe's own `schema` for its sheet's fields); paths are relative to the spec file's directory. Top level: `version`/`metadata`/`instances` (the project's canonical, ordered environment set — required even when every sheet overrides it, so there is one place a typo is caught and one place a reader sees the whole list) /`enrich` (`project`/`metadata_dirs`/`argument_specs`/`terraform_variables`/`lang`/`native_lang`/`strict`) /`capabilities`/`id_fields` (project-wide list-of-maps identity fields) /`sheets[]`. Per sheet: `name`/`recipe` (+ that recipe's own schema-validated fields) /`instances` (optional override, must be a subset of the top-level list, own order authoritative when given) /`dictionaries` (this sheet's own `SheetDictionaryBinding[]` — product/version/key_prefix/materialize, matched against ONLY this sheet's keys). `categories`/`under_key` used to be sheet fields here too — moved to the project metadata (sheet.yml) in P7, since both are display facts, not data-source ones; see `providers/project.ts`'s entry above and `assemble.ts`'s ghost-tab guard. Every object in the spec schema (root, `metadata`, `enrich`, `capabilities`) sets `additionalProperties: false`, and so must every recipe's own `schema` (`src/recipes/*.ts`) — without it a typo'd/removed field (`overlayz:` for `overlays:`, or a stale `keying:` a recipe never read) is silently ignored instead of rejected: the build succeeds, but the row/layer it would have populated is just gone, no error, no warning (the exact shape a per-sheet `keying:` switch's removal, S2, left behind in three PoC specs until this gate caught it). A sheet entry also carries spec-level fields no recipe schema declares (`name`/`recipe`/`instances`/`dictionaries` — `COMMON_SHEET_FIELDS`), so `loadBuildSpec` strips those before validating the rest against the recipe's schema, keeping "recipe's own fields" and "every sheet has" cleanly separate rather than making every recipe schema restate the common four. An `additionalProperties` rejection's message includes a "did you mean" hint (`suggestNearest`, reused from `assemble.ts` rather than a second copy of the same Levenshtein heuristic) when a declared field name is close
- `src/recipes/*.ts` — one `SheetRecipe` per project shape, self-registering at load like `src/parsers/*.ts`. `layered.ts` is the IaC-agnostic core every "one base + per-instance overlay" project shape reduces to: `defaults`/`overlays` (each one path or a list of paths, merged in declaration order — needed when a sheet's base is genuinely assembled from more than one file, e.g. one ECS task definition + one Dockerfile), keyed by each entry's extracted leaf name (`Entry.key`) — a same-file leaf-name collision (a TOML `[[array-of-tables]]`, a JSON array of objects sharing a field name) is a hard `buildMapFromSources` error with a suggested per-source `key`-transform fix, unlike the declared-sources override above (intentional) or `static_files` below (keys by structural path, never collides, and `origin: embedded` unless the entry declares `origin: default` — a file that RECORDS the product's own built-ins rather than shipping them, so its rows get no definition site, verify skips them and apply holds; rejected together with `substitution:`, which merges rows into variables the project does set — see SKILL.md's "`defaults`/`overlays` vs. `static_files`" section) + optional `static_files`, opt-in `include`/`exclude` key globs (`keyglob.ts` — an inventory with one group_vars file per HOST GROUP, the ordinary Ansible layout, holds every role's variables, so without a filter a one-role sheet files the other roles' variables as its own; NOT defaulted to "keys the defaults declare", since an overlay-only variable is a legitimate Pattern B row), and an optional per-source declarative key transform (`keytransform.ts` — a chain of regex/case steps applied AT EXTRACTION TIME, against a source's `Entry.key` or its full `Entry.source.path`, before entries are merged into an `ExtractedMap`; this is what lets a nested or repeated structure — hcl's `variable.<name>.default`, a JSON array element's `environment[name=X].value` — resolve to a flat project key space without a hand-written recipe. `AssembleHooks.keyFor` (assemble.ts) runs too late for this job: by the time a hook sees a parameter, entries whose leaf `Entry.key` collided have already overwritten each other in the map. A "drop" step is opt-in per step (default "keep"), and a "drop" pattern that never matched anything is reported back as a warning — silently losing rows is the one failure mode this whole area exists to prevent, see keyglob.ts's `unmatchedPatterns` for the same stance). `defaults` is optional here (omitted → empty base, mirroring `snapshot.ts`'s convention, so a sheet built purely from per-instance overlays still turns every key into a real Pattern B row). No `keyMap` here either — a plain base+overlay layer has no template to derive a product key from, so every row keeps its extracted identity verbatim. `ansible.ts` is now a thin specialization on top of `layered.ts` — it calls `layeredRecipe.load()` for the base/overlay/static_files/include-exclude plumbing and adds only what is genuinely Ansible-specific: Jinja2 `template` rendering, and — whenever a `template` is given, automatically, with no per-sheet flag (S2) — binding a role's `defaults` variables to the PRODUCT's own config keys via `SheetInputs.keyMap`, read off the template's `{{ ansible_var }}` passthroughs — but only for a variable that backs exactly one template entry; one driving two or more directives (httpd's `ProxyPass`/`ProxyPassReverse` sharing a backend variable) has no single product key to claim, so it is filed under ITS OWN NAME instead (no keyMap entry, hence no under_key either — see assemble.ts's `resolveKey`) and reported (`console.warn`, same style as this file's other `skipped (...)` warnings) naming the variable and every entry key it drives, never decided silently; a `defaults` variable the template never resolves into a row at all (never referenced, or only inside a conditional test) is rescued into the base map, appended after every template-derived one in `defaults`'s own order under its own name, ONLY when no overlay sets it either — otherwise it would be entirely invisible (this project never silently drops a row); one some overlay DOES set is left alone, since assemble.ts's own "keys seen only in overlays" sweep already recovers it with its true historical shape (a Pattern B row covering only the instances that set it) — rescuing it here too would fabricate a base value for every instance that never set it. **`templates:` (plural)** covers a sheet whose subject is SEVERAL deployed artifacts — a product's main config file, its systemd unit and its environment file are one subject to a reviewer, and an incumbent sheet being migrated from usually groups them that way. Each entry becomes a COMPONENT (id = the file name with `.j2` stripped, or a declared `component:`), which is what makes the merge possible at all: two systemd units both have `Unit.Description`, and the base map is keyed by the row's own name, so one would silently overwrite the other. Literals therefore go to `embedded[]` (a list, whose entries each carry a `component`) instead of the base map when a sheet is scoped — the same mechanism `static_files` already uses for several files on one sheet; the cost is that embedded rows are appended after the base layer rather than interleaved at their template position, which grouping by component reorders anyway. Variables stay in the SHARED base map keyed by the variable name, because that key is also the overlay lookup key — so per-environment values keep working untouched — and the existing not-1:1 rule is simply counted across the whole sheet: one variable spelling a directive in one file and its equivalent in a second is the same situation as `ProxyPass`/`ProxyPassReverse` sharing a backend, so it earns no product key, and no component either — it belongs to both files, and claiming one would be a guess, so the row sits outside every component heading. `template:` (singular) is unchanged and creates NO component: a sheet that IS one artifact needs no level naming it above every category, and existing sheets keep their row keys and their template-order interleaving byte for byte. Declaring both, or a sheet-wide `deployed_path` alongside `templates:`, is rejected rather than merged — which template the path belonged to would be a guess. `deployed_path` = the task's `dest:` → `Sheet.file_path` shows where the config LANDS and `Sheet.source_file` keeps the template, per the convention types.ts defines. A deployed `file_path` MUST come with `source_file`, else the verify/apply fallback would target a path on the managed host — read, or under `serve --write` written, on the reviewer's own machine. `snapshot.ts` (one PRE-RENDERED artifact per instance — `cdk synth`/`terraform plan`/`helm template` — for divergence that lives in program logic: emits an EMPTY base + one overlay per instance so every param is Pattern B, keys by structural path, marks every `source.generated: true` so `apply` HOLDS, and cuts the machine-generated noise down with `include`/`exclude` path globs via the same `keyglob.ts`, `*` within a segment / `**` across). Recipes NEVER execute a toolchain — artifacts are ordinary committed files. Custom recipes register the same way (CLI `--recipes-dir` / auto `./.review-sheet/recipes/`)
